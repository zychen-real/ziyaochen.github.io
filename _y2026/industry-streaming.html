01 · 摘要与关键结论

本次调研覆盖国内外头部互联网公司（字节、阿里、腾讯、快手、美团、小红书、京东、Meta、Google、Netflix/Pinterest）与开源生态（NVIDIA Merlin、TorchRec、Persia、Angel、XDL 等）在推荐模型流式训练（在线学习 / 近线增量）与在线部署（参数同步 / 热更新 / 模型管理）两个核心环节的公开方案。核心结论如下：

结论一：「分钟级参数同步」已成为行业事实标准。 字节 Monolith 稀疏参数分钟级增量同步（dense 天级）、小红书 LarC 分钟级闭环、阿里 PAI-ODL 5 分钟粒度增量 checkpoint、腾讯太极分钟级模型发布——头部公司的在线学习系统全部收敛到「分钟级」这一档。Monolith 在 Criteo 数据集上证明：同步间隔从 5h → 30min，在线 AUC 从 79.66 提升至 79.80；生产 A/B 中在线训练相比批训练 AUC 提升 14%~18%。
结论二：「Kafka 双流 + Flink 实时样本拼接」是样本链路的事实标准架构。 字节（特征流 + 行为流两条 Kafka，Flink Online Joiner 按 request key 配对）、阿里（Flink 特征预处理 / Feature Generation / Sample Generation）、小红书（Flink 实时拼接样本）均采用同构设计；延迟转化用「内存缓存 + 落盘 KV」二级结构承接，负采样配合 log-odds 校正保证样本无偏。
结论三：「无冲突动态 Embedding 表 + ID 生命周期管理」是稀疏参数工程的关键分水岭。 Monolith 用 Cuckoo HashMap 取代 hash trick（实验证明碰撞显著损伤 AUC），配合频次过滤（低频 ID 拒绝入场）与 TTL 过期（不活跃 ID 驱逐）控制内存；阿里 EmbeddingVariable、腾讯无量 tl_hash_map、NVIDIA HKV（LRU/LFU 驱逐）均为同思路实现。
结论四：部署侧形成「训练-推理分离 + 增量推送 / 版本化拉取」两大类机制。 推送派：Monolith 维护 touched-keys 集合，分钟级把增量稀疏参数从训练 PS 推到在线 Serving PS；拉取派：无量/PAI-ODL 走「导出 → 注册模型版本（complete/patch）→ Serving 定期查询并拉取」的模型管理路线，天然支持灰度与回滚。
结论五：生成式推荐（GR）正在重构「训练 + 部署」的整体范式。 Meta GRs/HSTU（1.5T 参数，线上 A/B +12.4%）与快手 OneRec（单模型替代召回→粗排→精排→重排级联，服务成本降至 1/10，已全量上线）证明：推荐系统正从「碎片级联 + 在线学习」走向「端到端大模型 + 奖励系统」，流式训练的样本形态（SID token 化）与部署形态（生成式推理）都将随之改变。
结论六：可靠性可以拿来换实时性。 Monolith 生产实践：PS 天级快照 + 0.01%/天故障率下，丢失单日单分片更新对模型质量几乎无损（等效损失 0.01% DAU 一天的反馈），从而把快照开销省下来支撑更高频的参数同步。这是流式系统工程化中极具启发性的 trade-off。

03 · 各公司方案详述

3.1 字节跳动 · Monolith：为在线训练而生的推荐系统

arXiv 2209.07663RecSys'22 ORSUM已开源BytePlus Recommend 落地

Monolith 是字节跳动针对「稀疏动态特征 + 概念漂移（Concept Drift）」两大推荐系统本质挑战设计的在线训练系统，论文与生产数据披露最充分，是流式训练领域的标杆方案。

核心设计一：无冲突 Embedding 表（Collisionless HashTable）

  • 基于 Cuckoo HashMap 实现稀疏参数存储，替代 TensorFlow 定长 Variable + hash trick，从根上消除 ID 碰撞（实验证明 7.7% 碰撞率即显著拉低 AUC，且随概念漂移持续恶化）；
  • 频次过滤：低频 ID（长尾、欠拟合）入场前拦截，阈值可调，另配概率过滤器进一步压缩内存；
  • 过期驱逐（Expirable Embeddings）：ID 按不活跃时长 TTL 过期，不同 embedding 表可配不同敏感度；
  • HashTable 实现为 TF 原生 resource op，lookup/update 与 Variable 同构，兼顾易用性与跨平台性。

核心设计二：流式引擎与在线样本链路

  • 延迟转化承接：内存缓存 + 落盘 KV 二级结构，用户几天后的转化行为仍能正确配对特征；
  • 负采样 + log-odds 校正：采样改变分布后，serving 侧做 log odds correction，保证在线模型是原始分布的无偏估计；
  • 批训与在线训练消费同一条样本 Kafka 队列，实现无缝切换（改结构重训历史数据 → 切回在线）。

核心设计三：增量在途参数同步

利用三个观察：① 稀疏参数占模型体积绝对大头；② 短时间窗内只有小部分 ID 被训练到；③ dense 变量在动量优化器下移动远慢于稀疏 embedding。Monolith 维护 touched-keys 哈希集合，分钟级把增量稀疏参数从训练 PS 推到在线 Serving PS（约 10 万 ID/分钟 × 1024 维 ≈ 400MB/分钟），dense 参数天级在低峰期同步。不需要双倍内存、不中断服务。

核心设计四：容错换实时

训练 PS 仅天级快照。按 0.01%/天的 PS 故障率、1000 分片测算：每 10 天丢失 1 个分片 1 天的更新，等效损失 0.01% DAU 一天的反馈——对模型质量几乎无损。由此省下的快照开销全部投向更高频的参数同步。

3.2 阿里 · XDL / PAI-ODL：双轨制实时深度学习

XDL 2019 开源（阿里妈妈）PAI-ODL（DataFun 分享）双轨校正

阿里的方案分两层：面向高维稀疏数据的训练框架 XDL（2019 年开源，核心贡献包括 EmbeddingVariable——基于 HashMap 的可伸缩 embedding，int64 key 避免特征冲突），以及构建在 PAI 之上的实时深度学习体系 ODL。

ODL Pipeline：四大模块 + 双轨校正

flowchart TB subgraph 数据层 A["流式数据 Kafka"] --> B["Flink：特征预处理 / Feature Generation / Sample Generation"] B --> C1["实时样本流"] B --> C2["Dump 至 MaxCompute 数仓"] B --- FS["Feature Store
(离在线特征一致性)"] end subgraph 在线链路 C1 --> D["PAI-DLC 在线训练"] D --> E["模型 Validation
(不达标 → Sample Replay / 回退)"] end subgraph 离线链路 C2 --> F["天级全量训练 + Batch Eval"] end E --> M["ModelCenter"] F -- "全量 base 模型校正" --> D F --> M M --> S["Serving 拉取最新合法模型"]
  • 双轨制精髓：在线流式数据难免有脏数据（重复样本、label 回流延迟），离线天级全量模型作为「较准确的 base」每日下发给实时训练做增量起点，实现误差校正——这是与字节「纯在线」路线的关键差异；
  • 秒级模型更新的关键：增量 checkpoint。全量模型几十 GB~TB 无法秒级加载，增量 checkpoint 只记录一段时间窗内的 key/value 变化（5 分钟粒度，体积仅兆级~上百兆），restore 时 dense 权重直接更新到模型本地内存，稀疏参数更新到在线 EmbeddingStore；
  • 增量模型同时加速离线 failover 恢复（59 分钟挂掉只回退 5 分钟，而非从头再来）。

EmbeddingStore：超大规模稀疏预测的三种 serving 方案

① 分布式存储

PS / Redis 式分布式 KV，通用但有网络开销。

② 业务分片优化

user embedding 按 ID 哈希 shard 到不同实例；小稀疏参数每实例全量备份，请求本地命中，显著降低 E2E 延迟。

③ 多层混合存储

单机内：热特征 DRAM（百纳秒）、温特征 PMEM（微秒）、冷特征 SSD；大部分请求命中 DRAM，实测优于跨网络分布式存储。

Serving 侧另有 Session Group 优化：单机包装 N 个独立 session（线程池隔离、绑核、NUMA 感知），底层共享同一套只读 variable（无锁），在保证 latency 的前提下提升整机 QPS。

3.3 腾讯 · 太极 + AngelPS + 无量：平台化与参数服务器双轮

太极一站式平台AngelPS（Angel 开源）无量（PCG）内部资料 + 公开报道

太极机器学习平台

  • 一站式覆盖特征管理 → 样本生产 → 模型训练 → 模型服务，广告场景全流程配置化、产品化；
  • 自研参数服务器 AngelPS：承载 10TB 级模型训练、TB 级模型推理，支持多维特征融合与复杂模型结构；
  • 分钟级模型发布上线；推理侧同时支持 CPU 与 GPU 加速，按在线推理的存储/计算特征做定制；
  • Light 训练加速框架（曾两刷 ImageNet 训练速度世界纪录）服务于广告粗排等场景。

无量：PS 架构的分布式机器学习框架（训练 → 模型管理 → Serving 闭环）

  • 版本化模型管理：模型命名含名称/分片/版本/类型（complete 全量 / patch 增量）/格式，训练导出 → 注册 → Serving 定期查询 → 拉取，支持「自动上线」与「指定版本」两种模式，天然具备灰度与回滚抓手；

3.4 快手 · Persia / OneRec：从百亿参数 PS 到生成式端到端

Persia 开源（arXiv 2111.05897）OneRec 生成式推荐已全量上线

Persia： hybrid 架构撑到 100 万亿参数

快手早期开源的大规模推荐训练系统，支持 100 万亿参数级别，是 Monolith 论文的重要相关工作之一，代表快手在「流式训练 + 超大稀疏模型」阶段的技术积累。

OneRec：端到端生成式推荐（2025，已全量生产化）

  • 单模型替代级联：一个模型覆盖召回、粗排、精排、重排，在全量候选空间深层求解；直指级联架构「反馈不闭环 + 算力碎片化（广义 MFU 或仅 1%）」的痛点；
  • Lazy Decoder Only（V2）：发现约 90% 算力耗在无直接 Loss 监督的 Encoder 上，几乎移除用户历史编码计算、算力集中到 Decoder——节省约 94% 训练资源，等量资源下模型从 0.5B 扩至 8B，损失随规模平滑下降（符合 Scaling Law 拟合）；
  • Reward System 三类奖励：兴趣偏好（多目标统一为 Logic 监督）、业务偏好（生态约束直接定义为 Reward，天级响应，样本量约传统 1/1000）、Format Reward（保证生成可解码为真实视频）；
  • 成本账：服务成本降至原系统 1/10 且效果更优（全量 QPS 对比胜出）；按 CPM 20 元、80% 计算毛利、H20 MFU 40% 折算，单次曝光可支撑约 7.6B 参数模型在线服务；在线激活参数约 250M，仍有 scale-up 空间；
  • 部署现状：短视频主场景、电商货架、本地生活全量上线；场景迁移周期约 1.5 个月；Tokenizer 仅靠内容训练，数月不更新也能编码新视频。

3.5 美团 / 小红书 / 京东

美团 · 图灵一站式平台

  • 围绕数据构建闭环：离线训练、模型管理（统一模型格式，支持分区模型与超大模型）、特征平台（线下统一口径 + 线上稳定获取）、AB 实验平台；
  • TensorFlow 分布式训练优化实践（tech.meituan.com，2021）被 Monolith 论文列为相关工作：基于 TF 的 key-value hash table 方案支持在线更新与特征驱逐；
  • 推理侧与 NVIDIA 合作将 CTR 模型部署到 GPU，CPU+GPU 异构并行计算优化。

小红书 · LarC：分钟级实时推荐

闭环流程：用户行为实时捕捉 → Flink 实时拼接生成样本 → 样本实时送 Serving 预估，同时短窗口累积样本做 Online Training → 更新参数立刻发布线上。全链路保持分钟级。底层为「超大规模无冲突参数服务器」，模型为多任务深度模型（点击/停留时长/点赞/收藏）。规模：2 亿 MAU，日用户行为样本几百亿级；2019 年启动，2020-2021 覆盖搜索/推荐/广告，2022 平台化。

京东 · 广告在线模型系统

公开资料以「在线模型系统分布式异构计算演变」为主：从缺乏统一架构的早期阶段，演进到架构统一、迭代效率提升的分布式异构（CPU+GPU）在线模型服务体系。在线学习细节披露有限。

06 · 架构范式归纳

业界方案可归纳为五种典型架构范式，实际系统常为多种范式的组合：

范式 A · 流式闭环在线学习代表：字节 Monolith、小红书 LarC

Kafka 双流 + Flink Joiner 实时产出样本，在线训练持续消费并更新训练 PS，touched-keys 增量分钟级推送 Serving PS。优势： freshest 模型、AUC 收益显著（+14~18%）；代价：样本链路复杂（延迟转化、负采样校正）、PS 需承载双份参数写入压力。

范式 B · 双轨制：天级全量校正 + 实时增量代表：阿里 PAI-ODL

在线流式训练追实时性，离线天级全量训练产出「干净 base」每日校正在线模型，增量 checkpoint（5min）解决大模型秒级上线问题。优势：抗脏数据、效果可兜底；代价：两套训练链路维护成本高。

范式 C · 平台化模型版本管理代表：腾讯无量/太极、美团图灵

以「训练 → 导出（complete/patch）→ 注册 → Serving 查询拉取」的模型管理闭环为中心，自动上线 + 指定版本双模式，天然支持灰度与回滚。优势：工程稳健、多业务复用；代价：实时性取决于导出/注册/拉取链路节拍。

范式 D · GPU 训推一体分层参数服务器代表：NVIDIA Merlin（SOK+HPS）

训练侧 HKV 把 embedding 分层放在 HBM+DRAM 并用 GPU 模型并行训练，推理侧 HPS 用 GPU Cache/DRAM/SSD 三级分层服务超大 embedding，UTC 阈值增量导出衔接两侧。优势：硬件利用率与成本最优；代价：GPU 资源投入大、生态绑定 NVIDIA。

范式 E · 生成式端到端（演进中）代表：快手 OneRec、Meta GRs

内容经 Tokenizer 化为 Semantic ID，推荐重构为序列生成任务，单模型替代级联全链路，Reward System 替代多目标拼接。部署从「PS + 打分服务」转向「生成式推理服务」。优势：链路一致性强、可 Scaling、成本反而下降（OneRec 1/10）；代价：范式颠覆、组织与基建均需重构。

07 · 趋势展望

1. 实时性：分钟级 → 秒级

参数同步间隔持续压缩（Monolith 已证明越短越好），瓶颈在网络与内存双写成本；增量同步 + 稀疏/稠密分级节拍是当前最优解，下一步是秒级稀疏推送与流式 dense 更新。

2. 生成式推荐重构训练与部署

Meta GRs（1.5T、+12.4%）与快手 OneRec（成本 1/10、全量上线）验证了范式可行性。样本形态从「ID 特征 + label」转向「SID token 序列 + Reward」，训练基建向 LLM 式大模型训练靠拢。

3. 训推全链路 GPU 化

Merlin 生态（HKV/SOK/HPS）打通 GPU 训练到 GPU 推理的增量链路；快手用「广义 MFU」衡量推荐算力效率（级联架构或仅 1%），GPU 化与端到端化是提升 MFU 的两条主线。

4. 特征平台标准化

Feature Store 成为离在线一致性的标准答案（阿里 PAI-ODL、美团特征平台、开源 Feast）；特征口径统一是流式训练不出错的前置条件。

5. 大模型与推荐深度融合

OneRec-Think 等探索把文本/语义 ID/图像 token 统一训练，指向「生成-理解」一体化全模态推荐基座；交互式推荐（用户显式表达意图）成为新交互形态。

6. 可靠性工程：从保守快照到量化 trade-off

Monolith 的「天级快照 + 故障损失量化测算」方法论将被更多系统采用——用数据证明模型对参数丢失的鲁棒性，把省下的资源投向实时性。
