生成式召回 RQ-KMeans-FSQ 方案技术分析

从 query2sid 任务的 hit 召回率差异出发,系统剖析 q-d 训练与 d2d 训练范式在生成式召回中的本质区别, 涵盖量化误差、码本分布、隐式对齐、蒸馏与多任务等核心话题; 并深入 RQ-KMeans + FSQ 四层结构的记忆/推理属性分层、SID 输入侧暴露的训练任务构造、 多任务训练顺序编排与长文档 indexing 的工程处理。
主题 GenIR · query2sid · RQ-KMeans · FSQ 日期 2026-09-15 QA 12 轮
Q1
为什么 q-d 召回向量训练表征,对比 d2d 训练的表征,在最终 query2sid 任务上正例 hit 召回率更高? 核心问题
核心原因:训练目标与最终任务的对齐性

q-d(query-doc)和 d2d(doc-doc)训练得到的向量空间语义结构完全不同, 而生成式召回(rq-kmeans-fsq 把向量量化成 semantic ID)极度依赖这个向量空间的"局部邻域是否就是 ground-truth"。

1. q-d 训练:空间结构 = 相关性结构
  • 训练目标(InfoNCE / 对比损失)直接优化 q 与 dpos 的相似度,最大化与 dneg 的差异。
  • 学到的向量空间,一个 query 的最近邻 ≈ 它想要的正例 doc 集合。
  • 量化(kmeans / FSQ)时,码本中心点自然落在"对一类 query 都相关"的 doc 簇上。
  • → query 量化得到的 semantic ID,与正例 doc 的 ID 共享长前缀的概率高。
2. d2d 训练:空间结构 = 内容结构,不是相关性结构
  • 训练只用 doc-doc 对(同主题/同实体聚集),query 完全没出现在训练中。
  • 学到的空间是"内容相似度空间",不是"相关性空间"。
  • 问题举例:
    • "iPhone 15 评测"、"iPhone 15 拆解"、"iPhone 15 维修"在 d2d 空间高度共簇(都是 iPhone 15)。
    • 但用户搜 "iPhone 15 续航",真正的正例是"评测"。
    • d2d 量化后,"续航"这个 query 的 embedding 被量化时,可能被分到"评测 / 拆解 / 维修"共用的同一个码字 → recall 中包含的真值 hit 反而少。
  • 本质:query 是外推的(out-of-distribution),向量空间没有为它对齐过相关性边界。
3. 量化误差放大 d2d 的劣势

rq-kmeans-fsq 是有损压缩,多级残差量化后,每个 doc 被压成一段短的 ID 序列。压缩粒度有限:

空间类型码字边界码字 → doc 集合hit 率
q-d 空间按"相关性"切一组强相关 doc高
d2d 空间按"内容相似"切一组主题相似但相关性混杂的 doc低
4. 码本容量分配不一致
  • q-d:正例 doc 在某些簇上集中(因为多个 query 都把它们当正例),码本在"相关边界"更密集。
  • d2d:所有 doc 几乎均匀占满码本,正例和负例混在一起。
5. 经验佐证(TIGER / GenRet / DSI 系列论文)

几乎所有 GenIR 工作都报告同一个结论:query-aware 训练显著优于 doc-only 训练。 原因正是 semantic ID 必须是"相关性指纹"而不是"内容指纹"。

q-d 训出来的向量空间本身就是"为 query 检索定制的",量化后得到的 semantic ID 是相关性指纹, query 与正例 doc 自然共享前缀;而 d2d 训出来的是内容指纹,query 在这个空间里是"局外人",hit 率天然低。
实践建议
  1. 双塔召回向量 + 生成式量化联合训练(端到端优化量化对召回的影响)
  2. Hard negative mining:让 q-d 训练的对比更精细
  3. 多任务:q-d 训练时同时加 doc-doc 辅助任务,保留 doc 侧的语义结构但不让它主导
Q2
d2d 是严格大模型打标过的(反驳:标签质量够好)
关键洞察:标签质量 ≠ 训练范式对齐

d2d 即便标签是严格大模型打标的高质量相关性标签,仍然在 query2sid 上输给 q-d, 是因为问题出在训练范式本身,不在标签。

1. 标签再好,query 也没进入向量空间
  • d2d 训练的 loss 只动 dpos ↔ dneg 的几何关系,query 完全不参与计算。
  • 训练结束后,向量空间里没有任何方向是为 query 优化的。
  • 即使你打标的 (dpos, dneg) 完美反映"对哪些 query 相关",这个信号也只是"doc 之间互相知道",query 永远是局外人。
  • → 量化码本只覆盖了 doc 分布,query 进来编码时没有为它准备的码字。
2. q-d 的不可替代性:query 和 doc 共空间 + 共码本
  • q-d 训练把 q 拉进同一个向量空间,loss 直接优化 sim(q, dpos)↑, sim(q, dneg)↓。
  • 向量空间的几何被压成"以 query 为中心,正例 doc 包围 query"的结构。
  • rq-kmeans-fsq 量化时,query 和 doc 共用一套码本 → 码字天然刻画"哪类 doc 对哪类 query 都相关"。
  • 这是 d2d 物理上做不到的,无论标签多准。
3. 量化瓶颈在 query 侧暴露

码本容量有限,kmeans/FSQ 只能把向量空间切成 K 个簇:

训练方式切出的簇语义
d2d"内容主题"(评测、菜谱、新闻…)
q-d"相关性主题"(续航相关、价格相关、做法相关…)

同一个 query "iPhone 15 续航":

  • d2d:被量化进"手机评测"码字 → 召回各种手机评测(正例稀疏、负例密集)
  • q-d:被量化进"续航相关"码字 → 召回真正答这个 query 的 doc
4. 大模型打标反而可能"过语义化"

这是一个更深的问题:语义相似度 ≠ 检索相关性。

  • 大模型打标倾向基于"内容/语义是否接近"判相关,但 query 召回关心的是"是否真能回答这个具体 query"。
  • 例:query "iPhone 15 续航",候选 doc:
    • D1: "iPhone 15 详细评测(含续航章节)" → 真正相关
    • D2: "iPhone 15 价格对比" → 语义相关但不相关于"续航"
  • 大模型可能给 D1、D2 都打"高相关性"(它们语义近),但 query 召回只想要 D1。
  • q-d 训练如果有真实点击/行为信号,能学到这种细粒度差别;纯 d2d 即便标签是 LLM 打的相关性,也只是 doc-doc 关系,没有 query 这个中介来区分。
5. 直觉比喻

d2d 训出来的向量空间像一本按内容主题分类的图书目录(菜谱区、评测区、新闻区…)。 q-d 训出来的向量空间像一份FAQ 索引("续航问题" → 续航相关 doc 簇)。 量化码本就是目录的章节。把 query "续航怎么样" 丢进去:在图书目录里,它被分到"评测区",但评测区里有无关 doc; 在 FAQ 索引里,它直接命中"续航相关"章节,hit 率高。

d2d 再怎么精心打标,学到的也只是"doc 内容相似度空间",码本切的是内容主题; query 没有进入模型,量化时 query 没有"专属位置"。q-d 把 query 拉进同一空间、共享同一码本, 码字自然按"相关性主题"切,query2sid 的正例 hit 率必然更高。
建议

如果一定要用 d2d 数据,至少在 d2d 预训练后用真实 q-d 监督信号继续微调 (或者直接用 query-doc 弱监督,比如点击日志),否则无论 d2d 标签多严格,query 侧的几何对齐都不会发生。

Q3
这个方案没有 qsid,直接 query 明文到 doc sid 的
关键区别:query 明文 → doc sid 的自回归生成

没有 qsid,意味着生成器(T5 类 encoder-decoder)从 query token 出发直接生成 doc 的 sid 序列。 召回时 beam search 出 sid,查 sid → doc 表。

这就把问题归结为:为什么生成器从 query 明文更容易生成 q-d 训出来的 sid,而不是 d2d 训出来的 sid?

核心原因:sid 序列本身是不是"query-friendly"
1. q-d 训出的 sid 编码了"对哪类 query 相关"
  • d2d 训出的 sid 是 doc 的内容指纹(哪些 doc 互相内容相似)。
  • q-d 训出的 sid 编码了"对哪些 query 都相关"的信息(因为 query 参与了 loss)。
  • 生成器从 query 明文出发要生成 sid 时,q-d 的 sid 跟 query 的语义更"贴合",生成难度低。
2. 多个正例 doc 的 sid 聚集度差异(最关键的点)

一个 query 通常对应 多个 ground-truth 正例 doc。hit 率取决于"一次 beam search 能覆盖多少正例 sid"。

  • d2d 训出来的 sid:同一 query 的多个正例 doc,因为内容主题不同 (例如"iPhone 续航"对应的正例可能是评测、对比、科普),被分散到不同簇,sid 前缀不重合。
    生成器一次只能走一条 sid 路径,要"蒙中"多个分散的正例 → 概率乘性下降 → hit 率低。
  • q-d 训出来的 sid:同一 query 的多个正例 doc 因为共享同一 query 信号, 被压到相同或相邻簇,sid 共享长公共前缀。
    生成器只要生成这个共有前缀,beam search 一次就能 hit 多个正例 → hit 率高。

这就是 "前缀重合假设":q-d 训练本质上是让"语义相关的 doc 共享码字前缀"。

3. 生成器的归纳偏置问题
  • T5 类自回归生成器擅长学习"输入语义模式 → 输出 token 序列"的直接映射。
  • q-d sid:query 语义 → sid 序列 是直接映射,学起来简单,泛化好。
  • d2d sid:query 语义 → sid 序列 中间隔了一层"query → doc 内容"的隐式推理,学起来难,泛化差。
  • 数据效率上:同样数据量,q-d 收敛更快、泛化更好。
4. 直觉比喻

d2d sid 像 ISBN 编号:每本书独立编号,内容相近的书编号也不连续。 q-d sid 像 Dewey 十进制分类:同一 query 想要的书集中在同一类目,共享前缀。 生成器从 query 出发:ISBN 方案要"记住"每个 query 对应哪些具体编号,几乎不可能一次全猜中; Dewey 方案生成"类目号"就能一次覆盖一片相关的书。

5. 量化误差 + 生成误差的叠加
  • d2d:多个正例分散 → 量化误差让它们离得更远 → 生成误差叠加 → hit 难
  • q-d:多个正例聚集 → 量化误差小(已经在同一簇)→ 生成只要走对一次 → hit 易
query2sid 是生成任务,hit 率取决于"生成一次能覆盖多少正例 sid"。q-d 训出的 sid 让同一 query 的多个正例 doc 共享长公共前缀,生成器一次生成就能命中多个;d2d 训出的 sid 让正例分散,生成器一次只能蒙一个,hit 率必然低。 前缀重合度就是核心。
实战建议
  1. 多正例聚类正则:训练向量化时显式加约束,让同一 query 的多个正例 sid 共享更长前缀。
  2. beam search + 前缀聚簇:召回时利用前缀聚簇做层次化剪枝,hit 率能再上一档。
  3. 混合训练:用 q-d 主 loss + 少量 d2d 辅助 loss,既保留 doc 侧内容结构,又让 query 侧对齐不丢失。
Q4
d2d 分的好不是坏事,query 引导的 doc 容易造成偏执
用户的论点解构
  1. d2d 训出的簇内 doc 是真正语义/内容相关的("dd 相关")。
  2. q-d 训出的簇内 doc 只是"对同一 query 相关",但 doc 之间内容可能差异大。
  3. 如果多个 doc 共享一个 sid(用来召回),那它们之间应该真正语义相关; 如果它们只因为"query 相关"被聚到一起,那 sid 内部就"脏"了。
  4. query 引导容易引入 bias(数据偏差、长尾分布)。

这个反驳在理论上是 partially correct 的!

澄清:query2sid 关心的是 query→doc 映射,不是 doc 间相似度
  • d2d 评估指标:doc 内部语义一致性(簇内 doc 互相像不像)。
  • query2sid 评估指标:给定 query,召回 TopK sid 里能 hit 多少 ground-truth 正例 doc。
  • 这两个指标不等价,甚至常常矛盾:
    • d2d 簇内纯净 → 但簇可能跟 query 想要的 doc 不对齐
    • q-d 簇内混杂 → 但簇跟 query 对齐好

"dd 相关才能保证真的相关是同一个 sid"是doc 视角的内在质量标准, 但 query2sid 的 hit 率是 query 视角的覆盖能力。这两个不是一回事。

关于"qd 偏执",要分两面看
确实存在的偏执(批评得对)
  1. 点击/曝光偏差:q-d 训练信号来自搜索日志,热门 doc 被反复曝光 → sid 偏向头部。
  2. query 多样性塌缩:一个 query 的多个正例被强制压成同一前缀,丢失了 doc 内部的多样性。
  3. 长尾 query 信号弱:训练样本少的 query,sid 表征不稳定。

这些是真实问题,不是幻觉。

但这个偏执对召回任务是 feature 不是 bug
  1. query 想要的就是覆盖多个角度:
    query "Python 教程" 真实想要的 doc 包括入门、数据分析、ML 教程,内容差异本来就大。 q-d 让它们共享 sid 前缀,beam search 一次召回三种类型 → 用户体验刚好。 d2d 把它们分到不同簇 → beam search 要"猜中"哪个具体子簇才能 hit → 漏召严重。
  2. 召回场景就是要"宁可相关不可替代":
    精排阶段再做多样性打分,召回阶段就是要先把跟 query 沾边的都捞回来。 q-d 的"偏执"恰好对应召回阶段的需求:宁可召回一些弱相关的,也不要漏掉强相关的。
  3. d2d 的"纯净"反而是 over-constrained:
    簇内 doc 真的语义相似 → 但 query 不一定就是要"语义相似的 doc"。 query "iPhone 15 续航" 想要的 doc 跟 query "iPhone 15 拆机" 想要的 doc 集合,重叠度不高。 d2d 把这些 doc 都分散到不同簇,簇跟 query 错位,hit 率自然低。
真正的 trade-off:纯度 vs 召回覆盖
维度d2dq-d
簇内语义一致性高低(混杂)
簇跟 query 对齐弱强
召回 hit 率低高
长尾/曝光偏差低高
文档侧内在质量高偏

对"簇纯度"的担心对应第 1、4、5 行;query2sid 的 hit 率指标对应第 3 行。优化目标选错维度,再纯净也没用。

关于"dd 相关才能保证真的相关是同一个 sid"这个直觉

直觉上"共享 sid = 语义相关"很自然,但这是从 doc 侧看的。

从 query 侧看,共享 sid = 对一类 query 都相关才合理。这两个定义哪个对,取决于你的下游任务是 doc 检索还是 query 召回。

query2sid 显然是后者。

如果下游真的是 doc-doc 检索(比如找相似 doc),那 d2d 确实更对;但既然任务是 query→doc,就要接受 q-d 的"偏执"是必要代价。

如何兼顾两边

如果既想要簇内纯净,又想要 query 对齐,可以考虑:

  1. 两阶段训练:d2d 先做内容聚类预训练 → q-d 微调对齐 query。损失加约束让正例 doc 共享前缀,同时 doc 之间余弦相似度不要塌缩。
  2. multi-task loss:L = Lqd + α·Ldd,α 调权重,平衡两边。
  3. hard negative mining:q-d 训练时精心选负例,避免引入过强的 query 偏差。
  4. 前缀长度自适应:同一 query 的正例 doc 强制共享前 N 级码字,但 N 不要贪大,保留 doc 内部多样性。
d2d 的"簇内纯净"是 doc 视角的内在质量,q-d 的"簇内偏执"是 query 视角的对齐代价。 query2sid 的 hit 率指标天然选后者,所以 q-d 胜出。但对"过度混杂"的担心不是没道理—— 簇内过度混杂会引入点击偏差,解决方案不是回到 d2d,而是给 q-d 加 d2d 正则或多任务约束。
Q5
d2d infer 时可以开 beam size 来保证多样性
beam size 能缓解多样性,但治标不治本

beam search 是从生成器的输出分布里挑 K 个最优序列。它放大了生成器已有的信号,但不能创造新信号。

具体来说:

  • 给定 query "iPhone 15 续航"
  • d2d 训出的生成器只知道"哪些 sid 经常出现",但不知道哪些 sid 跟这个 query 强相关
  • beam size = 10 时,它会输出 10 个 sid,但这些 sid 是"最可能的 sid",不是"最相关的 sid"
  • 如果 query 的语义信号跟 d2d 簇边界不对齐,开 100 的 beam 也只会从一堆不对齐的 sid 里挑

关键瓶颈是生成器本身的 query→sid 关联弱,不是采样数量。

真正的 trade-off
维度d2d + 大 beamq-d + 小 beam
簇内 doc 纯净度高低
簇跟 query 对齐弱(生成器弱关联)强
hit 率中(靠 beam 数量堆)高(一次就 hit 多正例)
计算成本高(beam=64+ 才稳)低(beam=8~16 就够)
长尾 query 表现差(信号稀疏)较好(共享前缀补偿)
召回稳定性弱(依赖 beam 数量)强(一次命中率高)
服务 latency高(大 beam 慢)低(小 beam 快)

d2d + 大 beam 是在用计算成本换 hit 率,而且换得不彻底 —— 因为生成器没学好,再大的 beam 也只能从不对齐的 sid 池里捞。

直观对比

q-d 训的生成器:知道 query "续航" → 直接生成"续航相关" sid 前缀。beam=4 就命中。

d2d 训的生成器:query "续航" → 输出分布里"评测"、"对比"、"科普" sid 都可能命中。beam=64 才能凑齐相关 sid,但里面可能混了无关 sid。

q-d 是"对准了再打",d2d 是"撒网打捞"。后者开大网也打不到不在水域里的鱼。

d2d + 大 beam 也有适用场景

坚持 d2d 的方向不是没道理:

  1. query 是 doc 标题/长 query 时:生成器能从字面推断 doc 内容主题,d2d 信号够用。
  2. 领域 doc 内容差异极大时(如医疗、法律专业文档):簇内纯净更重要。
  3. 不希望 query 侧偏差污染 sid时:d2d 的偏差源比 q-d 干净。
如果坚持 d2d 路线,工程上的优化
  1. 生成器训练时加 query 侧弱监督
    Ltotal = Ld2d + α · Lqd_weak
    让生成器既学到 doc 侧结构,又对齐 query。
  2. Diverse Beam Search + 簇内相似度惩罚
    • 用 DBS 而不是普通 beam,强制多样性
    • 加约束:选出的 sid 之间 doc 集合的 Jaccard 距离要够大
    • 避免 beam search 退化成"相似 sid 多次出现"
  3. 两阶段召回
    • 第一阶段:d2d 训的生成器开 beam=8,召回 ~50 个 sid
    • 第二阶段:用 query-doc 轻量双塔 rerank,过滤掉不对齐的 sid
    • 兼顾 d2d 的纯净和 q-d 的对齐
d2d + 大 beam 用计算成本换 hit 率,但生成器信号弱是天花板,beam size 突破不了。 q-d + 小 beam 用信号强度换 hit 率,天花板高、成本低。坚持 d2d 路线可以走,但建议加 q-d 弱监督做辅助任务, 或者用两阶段召回补 query 对齐,单纯堆 beam size 性价比不高。
Q6
d2d 向量如何能在 query2sid 模型上提高 query 和 doc 空间的隐式对齐
核心思路

d2d 训练出的向量空间里 query 是"局外人",要隐式提高对齐,本质是让 doc 表征在训练时"看到" query 侧的信号。 不直接用 q-d 监督信号,让 query 和 doc 在隐空间里"自然走到一起"。

方案一:共享预训练 backbone(最稳,零额外成本)

原理:预训练 LM(T5、BERT)已经在海量文本上学到了 query-like 文本和 doc-like 文本的语义对齐。 d2d 训练只是在这个基础上"精调" doc 侧结构。

实施:

  • 生成器(query→sid)用预训练 T5/BART
  • doc encoder 用预训练 BERT/RoBERTa
  • 关键:两者的底层 embedding 层共享或同源(如都用同一个 tokenizer 的 BERT 系)

为什么有效:即使 d2d 训练不动 query-doc 对齐,预训练已经把 query 和 doc 文本投到同一个语义流形。 d2d 只是细化 doc 侧结构,预训练的对齐基础还在。

优化点:在跟 query/doc 领域匹配的数据上继续预训练 MLM(如医疗、法律领域);让 backbone 见过更多 query-doc 交互的语料。

方案二:伪 query 自监督(最实用,推荐)

原理:doc 自己的标题、摘要、首段天然可以作为"伪 query"。 把这些伪 query 跟 doc 拉近,等于间接告诉 doc 表征"你会以什么形式被召回"。

# 伪 query 构造 pseudo_query = doc.title + " " + doc.summary + " " + doc.first_sentence # 训练时多加一个对齐 loss Ltotal = Ld2d + α · Lalign 其中 Lalign = -log( exp(sim(doc_emb, pseudo_query_emb)) / Σ exp(sim(doc_emb, qneg)) )

关键设计:

  • 伪 query 质量决定了天花板。用 doc 自己的"可能被搜到的表达"
  • 难负样本:从其他 doc 的伪 query 里采样
  • α 权重调平衡:太大退化成 q-d,太小没效果,建议 0.1~0.3

为什么是"隐式":没用到真实 query-doc 监督,伪 query 是 doc 自身衍生的。

→ 详见 Q7 完整展开

方案三:知识蒸馏(效果最好)

原理:训练一个轻量 q-d 双塔 teacher,用 teacher 的相似度分布作为软标签,蒸馏 d2d student。

# Teacher: q-d 双塔(可以用 BERT 双塔,只训 query-doc 匹配) teacher_qd_score = teacher_model(query, doc) # Student: d2d 训的 doc encoder student_doc_emb = student_doc_encoder(doc) # 蒸馏 loss: 让 student 的 doc 表征跟 teacher 的 q-d 分布对齐 Ldistill = KL(softmax(student_doc_emb @ query_emb / T), softmax(teacher_qd_score / T))

优势:

  • Student 主结构仍是 d2d(簇内纯净保留)
  • Teacher 的 q-d 信号通过软标签"灌"进去
  • 不需要 student 显式用 q-d pair 训练

注意:Teacher 自身要训好,否则噪声大;温度 T 调蒸馏强度(推荐 T=2~4)。

方案四:联合训练 doc 量化 + 生成器(理论最优)

原理:把 doc 的 RQ 量化跟 query→sid 的生成器端到端联合训练。 生成器的 loss 反向传播到 doc 量化阶段,让 doc 量化边界向"生成器容易生成"的方向调整。

doc → doc encoder → RQ 量化 → sid ↑ query → T5 生成器 → sid_pred (生成器 loss 反向影响 doc encoder + RQ)
L = Ld2d + β · Lgenerator(generator(query) → sid)

为什么理论上最优:doc 量化边界不再是"doc 分布主导",而是被"query→sid 的生成难度"反向约束。生成器学得轻松的 sid 划分方式会被保留。

挑战:端到端训练 RQ 量化梯度不稳定;需要 trick(如 straight-through estimator);实现复杂度高。

方案五:共享 vocab + token-level 对齐(补充技巧)

原理:让 query 和 doc 共用 tokenizer 和 embedding 表, doc 表征跟"它的相关 query token 的平均 embedding"对齐。

# 给 doc 收集一批相关 query 文本 query_token_emb = embedding_layer(query_tokens) # [N, D] query_mean_emb = query_token_emb.mean(dim=0) # [D] # 对齐 doc 表征到 query token 中心 Ltoken_align = MSE(doc_emb, query_mean_emb)

适用场景:query-doc 在词层面重叠度高的领域(如电商搜索,query 包含商品属性词)。

推荐组合策略
层次方案组合适用场景
轻量共享预训练 backbone + 伪 query 自监督(α=0.2)通用场景,零额外数据
中等轻量方案 + 知识蒸馏(teacher 用 q-d 双塔)有 query-doc 弱监督信号时
重型中等方案 + 联合训练 RQ + 生成器极致性能追求,可承担工程复杂度

大多数情况下"轻量方案"已经足够。预训练 backbone 提供了 60% 的对齐基础,伪 query 自监督再贡献 20~30%。 知识蒸馏和联合训练是锦上添花。

d2d 隐式 query-doc 对齐的核心是"让 doc 表征在训练时能感知到 query 侧的信号" —— 通过共享预训练 backbone(被动对齐)+ 伪 query 自监督(主动对齐)+ 蒸馏(强监督软化) 三种手段叠加,既保留 d2d 的簇内纯净,又提升 query 侧的召回能力。

二、编码器架构

推荐方案:共享底层 + 双塔顶

class DualEncoder(nn.Module): def __init__(self, pretrained_model): super().__init__() # 共享底层:BERT/RoBERTa self.shared_backbone = AutoModel.from_pretrained(pretrained_model) # 各自顶层 self.doc_head = nn.Linear(768, 768) self.query_head = nn.Linear(768, 768) def encode_doc(self, doc_text): emb = self.shared_backbone(doc_text).last_hidden_state[:, 0] # [CLS] return F.normalize(self.doc_head(emb), dim=-1) def encode_query(self, query_text): emb = self.shared_backbone(query_text).last_hidden_state[:, 0] return F.normalize(self.query_head(emb), dim=-1)

为什么共享底层:BERT 预训练时 query 和 doc 文本都在语料里,底层已经学到了通用语义对齐; 共享底层保留这个先验,顶层各自优化 doc 侧和 query 侧特性;工程上省一半参数。

更轻量替代:完全共享(不分手 head),适合小数据场景。

三、损失函数(核心)
3.1 基础对齐 loss(双向 InfoNCE)
def alignment_loss(d_emb, q_emb, temperature=0.05): """ d_emb: [B, D] doc 表征 q_emb: [B, D] query 表征 对角线是正样本对 """ B = d_emb.size(0) # 相似度矩阵 sim_d2q = d_emb @ q_emb.T / temperature # [B, B] sim_q2d = q_emb @ d_emb.T / temperature # [B, B] labels = torch.arange(B, device=d_emb.device) # 双向对称 loss loss = ( F.cross_entropy(sim_d2q, labels) + F.cross_entropy(sim_q2d, labels) ) / 2 return loss
3.2 多伪 query 对齐(每 doc 有 K 个伪 query)
def multi_query_alignment_loss(d_emb, q_embs, temperature=0.05): """ q_embs: [B, K, D] 每个 doc 的 K 个伪 query 表征 """ B, K, D = q_embs.shape # 展开成正样本对 d_expanded = d_emb.unsqueeze(1).expand(-1, K, -1).reshape(B*K, D) # [B*K, D] q_flat = q_embs.reshape(B*K, D) # [B*K, D] # 负样本:batch 内所有 doc 的所有伪 query all_q = q_embs.reshape(B, K*D) # [B, K*D] sim = d_expanded @ all_q.T / temperature # [B*K, B] labels = torch.arange(B, device=d_emb.device).unsqueeze(1).expand(-1, K).reshape(-1) # [B*K] return F.cross_entropy(sim, labels)
3.3 Hard Negative Mining
def alignment_loss_with_hard_neg(d_emb, q_emb, temperature=0.05, neg_topk=10): B = d_emb.size(0) sim = d_emb @ q_emb.T / temperature # [B, B] # mask 对角线(正样本) mask = torch.eye(B, device=d_emb.device, dtype=bool) sim_neg = sim.masked_fill(mask, -1e9) # 选 top-k hard negatives hard_neg_sim, hard_neg_idx = sim_neg.topk(neg_topk, dim=1) # [B, K] # 构造 loss:正样本 + hard negatives pos_sim = sim.diag().unsqueeze(1) # [B, 1] logits = torch.cat([pos_sim, hard_neg_sim], dim=1) # [B, K+1] labels = torch.zeros(B, device=d_emb.device, dtype=torch.long) return F.cross_entropy(logits, labels)

Hard neg 的作用:让模型关注"差点混淆的负样本",对齐精度更高。

四、与 d2d 主损失的结合

完整训练代码

class DocEncoderWithAlignment(nn.Module): def __init__(self, pretrained_model): super().__init__() self.encoder = DualEncoder(pretrained_model) # RQ 量化层 self.rq_layers = nn.ModuleList([ KMeansCodebook(dim=768, k=256) for _ in range(3) ]) def forward(self, doc_text, pseudo_query_texts): # doc 表征 d_emb = self.encoder.encode_doc(doc_text) # d2d loss(用 doc embedding 做对比) # ... 略,根据 d2d 训练范式 # 伪 query 对齐 loss q_embs = [] for pq in pseudo_query_texts: q_embs.append(self.encoder.encode_query(pq)) q_embs = torch.stack(q_embs, dim=1) # [B, K, D] Lalign = multi_query_alignment_loss(d_emb, q_embs) # RQ 量化 sid = rq_quantize(d_emb, self.rq_layers) return Lalign, sid # 训练 for batch in dataloader: doc_texts, pos_doc_texts, neg_doc_texts, pseudo_queries = batch # d2d 主损失 d_anchor = encoder.encode_doc(doc_texts) d_pos = encoder.encode_doc(pos_doc_texts) d_neg = encoder.encode_doc(neg_doc_texts) Ld2d = contrastive_loss(d_anchor, d_pos, d_neg) # 伪 query 对齐损失 q_embs = [encoder.encode_query(pq) for pq in pseudo_queries] Lalign = alignment_loss(d_anchor, q_embs) # 总损失 α = 0.3 # 平衡系数 Ltotal = Ld2d + α * Lalign # 反向传播 + RQ 量化联合训练 Ltotal.backward() optimizer.step()
五、超参数调优

α(对齐损失权重)

α 值效果
0.05几乎无影响,纯 d2d
0.1微弱对齐信号,簇内纯度几乎不变
0.2~0.3推荐范围,平衡对齐和纯度
0.5对齐明显,簇内纯度开始下降
1.0退化为 q-d 风格

调参方法:先 0.2,看 hit 率提升和簇内纯度下降的曲线,找拐点。

temperature(温度参数)

  • 默认 0.05~0.1
  • 小温度:分布尖锐,难样本学习充分
  • 大温度:分布平滑,泛化好
  • 推荐先用 0.05,观察效果

伪 query 数量 K

  • K=1:单伪 query,弱增强
  • K=3:推荐,正样本多样性足够
  • K=5:过多样本可能引入噪声

Q8
如果不动 d2d 表征、rq-vae 这些分词器件,只动 query2sid 任务,如何加强 query 和 doc 的隐式推理 约束优化
约束分析

能动的环节只有生成器(T5/BART)这一段:

  • d2d encoder:训出 doc embedding(冻结)
  • RQ-VAE/FSQ:把 embedding 量化成 sid(冻结)
  • query2sid 生成器:query → sid(唯一可优化环节)

要在生成器内部隐式建立 query→doc 的推理能力,本质是让生成器在生成 sid 时"心里有数"。

路径一:多任务辅助训练(推荐)

核心思想:生成器同时学 sid 生成 + 几个 doc 侧辅助任务,让它在内部隐式建立 query-doc 对齐。

# 主任务 Lmain = CE(generator(query), target_sid) # 辅助任务1:query → doc 标题 Ltitle = CE(generator(query, task="title"), doc.title) # 辅助任务2:query → doc 类别 Lcategory = CE(generator(query, task="category"), doc.category) # 辅助任务3:query → doc 关键词 Lkeyword = CE(generator(query, task="keyword"), doc.keywords) # 辅助任务4:query → 伪 query 改写 Lrewrite = CE(generator(query, task="rewrite"), pseudo_query) # 总损失 Ltotal = Lmain + 0.3·Ltitle + 0.2·Lcategory + 0.2·Lkeyword + 0.1·Lrewrite

为什么有效:生成器为了生成 sid,必须先在内部表征里"还原" doc 是什么。 辅助任务强迫它显式学这个过程。共享底层表示会让 sid 任务受益。

关键设计:

  • 用统一的 task prompt:"task=标题|生成|sid:{query}"
  • 所有辅助任务共享底层参数
  • 辅助任务的 label 都从 doc 元数据拿(不需要额外标注)
路径二:知识蒸馏(独立 q-d 双塔 teacher)

核心思想:训一个独立的 q-d 双塔 teacher,用 teacher 的相似度分布作为生成器的辅助监督。

步骤 1:训练独立 teacher
class QDDualTeacher(nn.Module): def __init__(self): self.q_encoder = AutoModel.from_pretrained("bert-base") self.d_encoder = AutoModel.from_pretrained("bert-base") # 不依赖 d2d encoder,独立训 def forward(self, query, doc): q_emb = self.q_encoder(query) d_emb = self.d_encoder(doc) return F.cosine_similarity(q_emb, d_emb) # 用真实 q-d pair 训(这算"半违规",但 teacher 独立不影响 d2d encoder) # 也可以用 doc 标题作为伪 query teacher = train_teacher(qd_pairs)
步骤 2:用 teacher 蒸馏生成器
# teacher 输出 query-doc 相似度 teacher_sim = teacher(query, doc) # [B] # 生成器中间隐层 → 投影到和 teacher 同一空间 student_proj = alignment_head(generator_hidden_states[:, 0]) # [B, D] student_sim = F.cosine_similarity(student_proj, doc_emb_for_teacher) # 蒸馏 loss Ldistill = MSE(student_sim, teacher_sim.detach()) # 总损失 Ltotal = Lmain + 0.5 · Ldistill

优势:不动 d2d encoder 和 RQ-VAE;teacher 完全独立,训坏不影响主流程; 生成器隐式吸收 q-d 对齐知识。

路径三:Soft Prompt Tuning(参数高效)

核心思想:加可学习的 soft prompt embedding,专门优化 query→sid 映射。

# 固定的 hard prompt hard_prompt = "基于以下查询生成对应的语义ID:" # 可学习的 soft prompt soft_prompt = nn.Parameter(torch.randn(20, 768)) # 20 个 token # 输入:hard_prompt + soft_prompt + query input_embeds = embed(hard_prompt) + soft_prompt + embed(query) # 只训 soft_prompt 和 alignment head,冻结 T5 主干

进阶:分级 soft prompt

# 给 sid 每一级码本单独的 soft prompt soft_prompts = nn.ParameterList([ nn.Parameter(torch.randn(10, 768)) for _ in range(num_levels) ]) # 训练时,按 sid 级别逐步喂入 # 生成第一级 sid 时用 soft_prompts[0] # 生成第二级 sid 时用 soft_prompts[1]

优势:训练成本极低(只训 0.1% 参数);soft prompt 可以专门吸收 q-d 对齐信号;推理时无额外开销。

路径四:Query 改写 + 测试时增强

核心思想:推理前用 LLM 改写 query,往 doc 侧语言风格靠拢。

改写模板
REWRITE_PROMPT = """你是搜索专家。请将用户查询改写为更适合检索文档的形式。 要求: - 提取核心实体和意图 - 使用更书面、更完整的表达 - 保留原意 用户查询:{query} 改写后:""" def rewrite_query(query, llm): return llm.generate(REWRITE_PROMPT.format(query=query))
进一步:检索增强改写
# 步骤1:用 query 检索相关 doc(用 BM25 或独立双塔) related_docs = retrieve(query, top_k=5) # 步骤2:用相关 doc 扩展 query expansion_prompt = f"""基于相关文档,改写查询: 原始查询:{query} 相关文档摘要:{[doc.summary for doc in related_docs]} 改写后:"""

优势:完全不动模型;改写一次,所有下游任务受益;可解释性强。

路径五:推理时 Rerank

核心思想:生成 K 个 sid 后,用独立 q-d 双塔 rerank 选最相关的。

# Step 1: 生成器 beam search 出 K 个 sid candidate_sids = generator.beam_search(query, beam_size=64) # [K] # Step 2: 每个 sid → 候选 doc candidates = [] for sid in candidate_sids: docs = sid_to_docs[sid] # 查 sid-doc 表 candidates.extend(docs) # Step 3: 用独立 q-d 双塔 rerank scores = rerank_model(query, candidates) # [N] top_docs = candidates[scores.topk(K).indices]

关键:rerank 模型可以是独立的、与 d2d 完全解耦的 q-d 双塔。 这是最干净的"不动 d2d 但补 query 对齐"的方案。

路径六:Hierarchical Generation

核心思想:把 sid 生成拆成多步,先生成粗粒度前缀,再生成细粒度后缀。

# 训练时 # 阶段1:生成 sid 第一级码字(粗粒度,簇级) prefix_logits = generator(query, generation_step=1) prefix_ids = prefix_logits.argmax() # 阶段2:基于 prefix 生成 sid 后续码字(细粒度,doc 级) suffix_logits = generator(query, prefix=prefix_ids, generation_step=2) suffix_ids = suffix_logits.argmax() # 多步 loss 累加 L = L_step1 + L_step2

优势:每一级聚焦一个语义粒度;生成器内部自然学到了"先粗后细"的推理;跟 RQ 多级码本结构天然匹配。

推荐组合策略
层次方案效果预期实施成本
轻量Query 改写 + 推理时 rerank+10~20% hit 率低
中等多任务辅助 + Soft Prompt Tuning+20~40% hit 率中
重型独立 q-d teacher 蒸馏 + 多任务+40~60% hit 率高

推荐的"中等方案"组合:

  1. 多任务辅助训练(让生成器内部隐式学 q-d 对齐)
  2. Soft Prompt Tuning(参数高效微调 query→sid 映射)
  3. 推理时 query 改写(测试时增强)
  4. 配合 beam search + rerank(最终召回)

这套组合完全不动 d2d encoder 和 RQ-VAE,只在生成器侧最大化 query-doc 的隐式推理能力。

不动 d2d 表征和量化器,要提升 query-doc 隐式推理,核心是让生成器"在生成 sid 时心里有 doc" —— 多任务辅助训练让它内部隐式学 q-d 对齐,独立 q-d teacher 蒸馏给它注入对齐知识, soft prompt 高效微调 query→sid 映射,推理时 query 改写 + rerank 兜底召回质量。 这套组合拳把"不动约束下的对齐能力"推到极致。
Q9
sid 前两层 RQ-KMeans + 后两层 FSQ,query2sid 偏记忆还是推理?sid 要在输入侧还是输出侧见过? 结构剖析
先拆结构:这 4 层不是同质的

RQ-KMeans 两层 + FSQ 两层,本质是两种性质完全不同的量化器串联,任务属性必须分层看:

层级量化器码本性质语义粒度一个码字覆盖 doc 数任务属性
L1RQ-KMeans可学习中心点,码字间有距离结构粗语义簇数千~数万推理主导
L2RQ-KMeans可学习中心点,残差聚类细语义簇数十~数百推理为主,记忆渗入
L3FSQ固定网格,无可学习中心残差细节个位数记忆主导
L4FSQ固定网格残差细节~1(近似唯一)纯记忆

关键差异:RQ-KMeans 的码字是数据驱动的中心点,码字 ID 相邻 ≠ 语义相邻,但码字所代表的向量簇有明确语义, 模型可以从 query 语义"推"出该落哪个簇。FSQ 是固定网格(每维独立量化到 L 个 level), 码字是残差向量的坐标编码,query 语义与 FSQ 码字之间几乎没有可学习的映射规律 —— 只能硬记。

答案:分层混合,且是"前推理后记忆"
L1/L2 是推理任务
  • 生成器要做的是:理解 query 意图 → 判断该落哪个语义簇。
  • 这是可泛化的:训练时没见过的 query,只要语义落在已有簇里,模型能推出正确前缀。
  • 这部分的能力来自 T5 预训练的语义理解 + query→簇 的映射学习。
L3/L4 是记忆任务
  • FSQ 层编码的是"这个 doc 在簇内的精确坐标",跟 query 语义没有任何可推理的关联。
  • 模型只能靠 (query, sid) 共现频次硬背。
  • 长尾 doc 在 L3/L4 上几乎必然错,因为训练样本里出现次数太少。
实测特征(可验证)

分层统计 accuracy,大概率会看到:

L1 acc: 85~92% （推理，泛化好） L1L2 acc: 60~75% （还能推） L1L2L3 acc: 30~45% （断崖，开始记忆） 全 4 层 acc: 15~30% （纯记忆，长尾崩）

如果你的曲线是这个形状,说明瓶颈在 FSQ 两层,不在 query 理解。

第二个问题:输入见过 vs 输出见过

结论:两边都要见过,但作用机制完全不同,且"输入侧见过"是被严重低估的关键。

暴露方式具体任务形式训练到的东西对 query2sid 的贡献
仅输出侧query → sid(主任务)decoder 的 sid 生成概率学会映射,但 sid token embedding 无语义锚
输出侧(indexing)doc_text → sidsid 与内容的绑定必须,建立 sid 的"身份"
输入侧sid → doc_title/keywordssid token embedding 获得语义 grounding决定泛化上限
输入侧sid_prefix → 补全 sid层级结构先验帮 beam search 剪枝
为什么"输入侧见过"这么关键

T5 的 sid token 是新扩的 vocab,初始化是随机的。

  • 只在输出侧出现:这些 embedding 只通过 softmax 的分类梯度更新,学到的是"在什么 context 下该输出我",embedding 本身没有语义内容。
  • 在输入侧出现(比如 sid → 生成 doc 标题 这个任务):embedding 被迫编码"我代表什么内容",它在 embedding 空间里的位置会靠近对应的语义区域。

一旦 sid embedding 有了语义位置,query → sid 的生成就从"查表"变成了"语义匹配",推理能力才真正建立。

特别注意:tied embedding

T5 默认 input embedding 和 output projection 权重共享。 这意味着输入侧的语义训练信号会直接传导到输出侧的生成 logits。 这是"输入侧见过"能提升 query2sid 的物理通道。

如果你的实现里解绑了 embedding(untied),这个增益会消失一大半,务必确认。

针对这个结构的具体建议
1. 多任务配比(关键)

DSI 系列的实证结论:indexing 任务和 retrieval 任务的比例要远大于 1(论文里用到 32:1)。 你这个结构因为有 FSQ 记忆层,建议:

tasks = { "doc2sid": weight=1.0, ratio=16, # indexing，建 sid 身份 "sid2doctitle": weight=0.5, ratio=8, # 输入侧暴露，给 sid embedding 语义 "pseudoq2sid": weight=1.0, ratio=8, # 伪 query，扩充 retrieval 覆盖 "query2sid": weight=1.0, ratio=1, # 主任务 }

sid2doctitle 这个反向任务是很多实现漏掉的,但对这种有 FSQ 层的结构增益最大, 因为它是唯一能给 L3/L4 token 注入语义的方式。

2. 分层 loss 加权

FSQ 两层本来就学不好,硬压 loss 会挤占 L1/L2 的容量:

layer_weights = [1.0, 1.0, 0.6, 0.4] # L1 L2 L3 L4 loss = sum(w * CE(logits[i], target[i]) for i, w in enumerate(layer_weights))

让模型把容量优先花在能推理的前两层。

3. 更激进:干脆别生成 L3/L4

这是更推荐的做法。既然 L3/L4 是纯记忆且必然不准:

Step 1: 生成器只生成 L1L2 前缀（beam=32） → 32 个前缀，每个覆盖数十~数百 doc Step 2: 展开前缀下所有 doc（约 1k~5k 候选） Step 3: 用轻量 q-d 双塔 rerank → TopK

hit 率通常能涨 2 倍以上,因为把"不可推理的部分"从生成任务里摘出去了, 交给了真正擅长精排的模块。代价是需要维护 prefix → doc_list 的倒排,内存换召回。

4. 前缀树约束解码

L1/L2 必须上 constrained beam search(Trie 约束),否则会生成不存在的前缀,白白浪费 beam 位置。

这在你的结构下尤其重要:RQ-KMeans 两层的组合空间是 K1 × K2,但实际有效前缀远少于这个数(很多组合是空的)。

5. 诊断实验(先做这个)
# 实验：只训 L1L2（把 L3L4 从 target 里截掉） # 对比：全 4 层训练时的 L1L2 accuracy # 如果 只训L1L2 的 acc 明显更高 # → 说明 FSQ 层在抢容量，方案 2/3 有效 # 如果 两者接近 # → 说明瓶颈在 query 理解，需要加强 indexing/输入侧任务
RQ-KMeans 2层 + FSQ 2层的结构,前两层是推理任务、后两层是记忆任务,两者的最优训练策略是冲突的。 SID 需要在输出侧见过(indexing 建身份)且在输入侧见过(sid→text 给 embedding 语义锚), 后者靠 tied embedding 传导到生成侧,是泛化能力的真正来源。 最高 ROI 的改动是:加 sid→doc_title 反向任务 + 只生成 L1L2 前缀后接 rerank。

前置:SID 的 token 化约定

先统一表示,后面所有样例都基于这个:

# 4 层 sid → 4 个特殊 token # L1/L2: RQ-KMeans，K=256 # L3/L4: FSQ，每层 level 数较小（假设 8） sid = "<a_137><b_42><c_5><d_2>" # vocab 扩展 new_tokens = ( [f"<a_{i}>" for i in range(256)] + [f"<b_{i}>" for i in range(256)] + [f"<c_{i}>" for i in range(8)] + [f"<d_{i}>" for i in range(8)] ) tokenizer.add_tokens(new_tokens) model.resize_token_embeddings(len(tokenizer))

每层用独立前缀(a/b/c/d),不要跨层复用 token, 否则 L1 的 <137> 和 L2 的 <137> 会共享 embedding,语义污染。

任务 1:sid2title(最核心)

作用:强迫 sid token embedding 编码"我代表什么内容"。

输入: 解码语义ID对应的文档标题: <a_137><b_42><c_5><d_2> 输出: iPhone 15 Pro 全面评测：续航提升 20%，A17 芯片实测 输入: 解码语义ID对应的文档标题: <a_137><b_42><c_3><d_7> 输出: iPhone 15 与 iPhone 14 对比：值不值得换 输入: 解码语义ID对应的文档标题: <a_88><b_201><c_1><d_4> 输出: 家常红烧肉做法，三步搞定不翻车

变体(推荐同时加) —— 只给前缀,输出该簇的"主题概括":

输入: 描述语义ID簇的主题: <a_137><b_42> 输出: iPhone 15 系列产品评测与对比 输入: 描述语义ID簇的主题: <a_137> 输出: 智能手机数码产品

任务 2:sid2query(逆任务,价值被低估)

作用:直接建模 sid → query 分布,是 query → sid 的镜像。tied embedding 下梯度互通。

输入: 生成可能检索到该文档的用户查询: <a_137><b_42><c_5><d_2> 输出: iPhone 15 续航怎么样 输入: 生成可能检索到该文档的用户查询: <a_137><b_42><c_5><d_2> 输出: iPhone15 Pro 电池实测 输入: 生成可能检索到该文档的用户查询: <a_137><b_42><c_5><d_2> 输出: A17 芯片性能

关键:同一个 sid 配 3~5 个不同 query (真实 query 日志优先,没有就用伪 query)。这教会模型"一个 sid 对应一片 query 语义区域",而不是一对一映射。

任务 3:sid_completion(层级先验)

作用:学习码本的有效组合空间,避免生成不存在的前缀。

输入: 补全语义ID: <a_137><b_42><c_5> 输出: <d_2> 输入: 补全语义ID: <a_137><b_42> 输出: <c_5><d_2> 输入: 补全语义ID: <a_137> 输出: <b_42><c_5><d_2>

注意:同一个前缀会对应多个合法后缀(因为多个 doc 共享前缀)。 这不是噪声,恰恰是让模型学到后缀分布,beam search 时才知道该展开哪几个分支。

任务 4:q_sid_match(判别式)

作用:生成任务只有正样本,没有"什么是错的"信号。判别任务补上。

输入: 判断查询与语义ID是否相关: 查询=iPhone 15 续航 语义ID=<a_137><b_42><c_5><d_2> 输出: 相关 输入: 判断查询与语义ID是否相关: 查询=iPhone 15 续航 语义ID=<a_88><b_201><c_1><d_4> 输出: 不相关

负样本采样策略(重要):

def sample_negatives(query, pos_sid, all_sids, n=3): negs = [] # 1) hard neg: 同 L1 前缀，不同 L2（最有价值） same_l1 = [s for s in all_sids if s[0] == pos_sid[0] and s[1] != pos_sid[1]] negs += random.sample(same_l1, min(2, len(same_l1))) # 2) easy neg: 完全不同 L1 diff_l1 = [s for s in all_sids if s[0] != pos_sid[0]] negs += random.sample(diff_l1, 1) return negs[:n]

Hard negative(同 L1 不同 L2)是提升 L2 层精度的关键。

任务 5:prefix2sid(专治 FSQ 层)

作用:L3/L4 的 FSQ 是纯记忆,单独给它们"减负训练" —— 已知前缀 + query,只补后缀。

输入: 已知前缀补全: 查询=iPhone 15 续航 前缀=<a_137><b_42> 输出: <c_5><d_2>

这比让模型从零生成 4 层容易得多,相当于把难任务拆成两个简单任务。 训练时加这个,推理时也可以用两阶段解码:

# Stage 1: query → L1L2 前缀（beam=32） prefixes = model.generate(f"检索: {query}", max_len=2, num_beams=32) # Stage 2: 对每个前缀，补 L3L4 for p in prefixes: suffix = model.generate(f"已知前缀补全: 查询={query} 前缀={p}", num_beams=4)
任务 6 & 7:轻量补充
# sid2keywords 输入: 提取语义ID对应文档的关键词: <a_137><b_42><c_5><d_2> 输出: iPhone 15 Pro, 续航测试, A17芯片, 电池容量 # sid_neighbor（学码本几何） 输入: 找出与该语义ID内容最接近的语义ID: <a_137><b_42><c_5><d_2> 输出: <a_137><b_42><c_3><d_7>

sid_neighbor 的 label 从 d2d 向量空间的最近邻直接拿 —— 这是唯一能把 d2d 训练的几何结构显式教给生成器的任务。 既然 d2d encoder 冻结了,这个任务能把它的知识"蒸馏"进生成器。

1. tied embedding 不能解绑

2. 新 token 的 embedding 初始化

Q11
我是先训 query2sid,还是 sid2query 类似的任务呢? 训练编排
结论:先 sid2query/sid2title,但不能"训完再切"

核心原则:先建立 sid 的身份与语义,再学 query→sid 的映射。 但必须用配比渐变,不能做阶段性硬切换。

为什么不能先训 query2sid

这是最关键的一点,涉及一个不可逆的局部最优陷阱:

  • sid token embedding 是随机初始化的。
  • 早期跑 query2sid,梯度只来自 softmax 分类损失,它的优化方向是 "让这些 embedding 彼此可区分",而不是"让它们有语义"。
  • 模型很快会找到一个解:把 sid embedding 推到互相正交的随机位置, 然后靠 decoder 硬记 query→ID 的映射。这个解 loss 降得很快,但完全没有泛化能力。
  • 一旦陷进去,后面再加 sid2title,需要把 embedding 从"正交散开"拉回"语义聚集", 这是一次大范围的表征重组,代价极高且经常拉不回来。

反过来先训 sid2title/sid2query:embedding 先占据语义位置, query2sid 再进来时,它面对的是一个已经有结构的目标空间,学的是"语义匹配"而不是"查表"。

实测规律:先输入侧后主任务 vs 先主任务后输入侧, 前者的最终 hit 率通常高 30%~50%,且长尾差距更大。

但也不能只先训 sid2query

两个问题:

  1. decoder 从没练过生成 sid。sid2query 的输出是自然语言, decoder 侧的 sid 生成路径(包括约束解码所需的层级先验)完全没训到。
  2. 纯串行会灾难性遗忘。切到 query2sid 阶段后, 如果输入侧任务归零,sid embedding 的语义会在几千步内被冲掉。
容易忽略的点:doc2sid 才是真正的第 0 步

严格说,最先要有的不是 sid2query,而是 doc2sid(indexing)。

原因:sid2query 和 sid2title 是"解释 sid 是什么", 但模型得先知道"这个 sid 属于谁"。doc2sid 建立 sid ↔ doc 的身份绑定,是其他一切任务的前提。

所以真实顺序是:

doc2sid（身份） → sid2title/sid2query（语义） → query2sid（映射）

三者在时间上重叠推进,只是权重峰值依次后移。

三个阶段的意图:

  • Phase 1 — 建身份 + 注语义:query2sid 几乎不训(ratio ≤ 1,仅作 warmup 探针用)。 目标是让 sid embedding 站到正确的语义位置。
  • Phase 2 — 补结构 + 加判别:引入层级先验(sid_completion)和负样本信号(match)。 query2sid 小比例进入,检验前期 grounding 是否有效。
  • Phase 3 — 主任务收敛:query2sid 主导, 但输入侧任务保留在 20~25% 的总量,防遗忘。

Phase 3 的输入侧任务绝对不能归零,这是很多实现翻车的地方。

阶段切换的判据:用探针 gate,不要用固定步数

比按 step 百分比硬切更稳的做法是用语义探针做门控:

def should_advance_to_phase2(model, tokenizer, docs): sim_real, sim_shuffled = probe_sid_semantics(model, tokenizer, docs) # sid embedding 与对应 doc 标题 embedding 的相似度 # 显著高于随机配对，说明 grounding 已建立 return (sim_real - sim_shuffled) > 0.20 and sim_real > 0.30 def should_advance_to_phase3(model, eval_set): # L1L2 前缀准确率达标，说明"推理层"已经学会 return eval_l1l2_accuracy(model, eval_set) > 0.55

判据的设计逻辑:

  • Phase 1→2 的门槛是"sid 有语义了吗"(embedding 层面)
  • Phase 2→3 的门槛是"能推对簇了吗"(L1L2 前缀准确率,这是可推理部分)

如果 Phase 1 跑了很久探针还是不动(sim_real - sim_shuffled < 0.1), 大概率是 tied embedding 被解绑了,去检查配置。

平滑过渡的实现

不要用 if step < X: return ratio_A,用插值:

PHASE_RATIOS = { 0.00: {"doc2sid": 20, "sid2title": 16, "sid2query": 12, "query2sid": 1, ...}, 0.25: {"doc2sid": 10, "sid2title": 10, "sid2query": 10, "query2sid": 3, ...}, 0.65: {"doc2sid": 4, "sid2title": 4, "sid2query": 5, "query2sid": 12, ...}, } def get_ratio(step, total): p = step / total keys = sorted(PHASE_RATIOS) lo = max(k for k in keys if k <= p) hi = min((k for k in keys if k > p), default=lo) if lo == hi: return PHASE_RATIOS[lo] w = (p - lo) / (hi - lo) return { t: PHASE_RATIOS[lo][t] * (1 - w) + PHASE_RATIOS[hi][t] * w for t in PHASE_RATIOS[lo] }

硬切换会造成 loss 尖峰和表征震荡,线性插值能显著平滑。

sid2query 与 query2sid 互逆的提醒

这两个任务方向相反,同时训不会互相干扰,反而互相增强 (类似 dual learning / back-translation 的机制)。但前提是:

task prefix 必须做强区分,否则模型会混淆生成方向。

# 好的做法：前缀在语义和字面上都有明显差异 "检索查询生成语义ID: iPhone 15 续航" → "<a_137><b_42><c_5><d_2>" "根据语义ID反推用户查询: <a_137><b_42><c_5><d_2>" → "iPhone 15 续航怎么样" # 差的做法：前缀相似，模型容易串 "query2sid: ..." / "sid2query: ..." # 字面太像，共享大量 token

如果发现模型在 query2sid 任务上偶尔输出自然语言(而不是 sid token),就是 prefix 区分度不够。 可以加一个输出空间约束兜底:query2sid 解码时只允许 sid vocab。

如果资源有限,只能做减法

按砍掉的代价从小到大:

  1. 先砍 sid_neighbor、sid2keywords(锦上添花)
  2. 再砍 prefix2topic(需要 LLM 离线归纳簇主题,成本高)
  3. 再砍 q_sid_match(判别信号,有 hard neg 才有价值)
  4. doc2sid / sid2title / sid2query / query2sid 这四个是底线,一个都不能少

其中 sid2title 是投入产出比最高的单个任务 —— 如果只能加一个输入侧任务,就加它。

顺序是 doc2sid(建身份)→ sid2title/sid2query(注语义)→ query2sid(学映射),但要用配比渐变而非阶段硬切。 先训 query2sid 的致命问题是 sid embedding 会被推向"可区分但无语义"的局部最优,事后极难纠正; 而 Phase 3 输入侧任务归零则会导致语义遗忘。 阶段推进用 sid embedding vs title embedding 的相似度探针做 gate,比固定步数更可靠。
Q12
但是我的 doc 都很长怎么办? 工程实践
好消息:长文档只影响一个任务

回顾任务清单,看输入/输出的长度:

任务输入输出受长文档影响
doc2siddoc 全文sid(4 token)是,唯一痛点

所有输入侧任务(给 sid 注语义的那些)都不受影响,因为它们的输入是 sid、输出是短文本。 真正要解决的只有 doc2sid 这一个。

最关键的原则:doc2sid 的输入必须与 d2d encoder 对齐

这是最容易被忽略、但影响最大的一点。

你的 sid 是 d2d 向量量化来的。那么问题是:d2d encoder 当初是怎么处理长文档的?

  • 如果 d2d encoder 只看了前 512 token → sid 编码的就是前 512 token 的语义
  • 这时 doc2sid 如果喂全文(或喂摘要),target sid 反映的内容和 input 不一致 → input-target mismatch,模型学到的是噪声
# 检查你的 d2d encoder 配置 d2d_max_len = d2d_encoder.config.max_position_embeddings # 512? 1024? d2d_truncation = "head" # or "head_tail" / "chunk_mean" # doc2sid 的输入构造必须复刻这个逻辑 def build_doc2sid_input(doc): return apply_same_truncation(doc.text, d2d_max_len, d2d_truncation)

如果 d2d 是分块编码后取平均的,那 doc2sid 也应该用多个块分别作为输入、 映射到同一个 sid(见下面的多视角方案),而不是喂全文。

先去确认这一点,比选哪个截断策略重要得多。

方案一:first-k 截断(强 baseline,别过度设计)

DSI 论文做过文档表示的消融实验,结论反直觉: 直接取前 L 个 token(Direct Indexing)比 Set Indexing、Inverted Index 等复杂策略效果更好。

def doc2sid_input(doc, max_len=512): return f"索引文档: {doc.text[:max_len]}"

为什么有效:

  • 大多数文档的核心信息集中在开头(标题、导语、首段)
  • 长尾部分往往是细节、引用、无关内容,对建立 sid 身份反而是噪声
  • 训练效率高,batch 能开大

建议长度:256~512 token。超过 512 边际收益急剧下降。

方案二:多视角片段 → 同一 sid(推荐)

从文档不同位置采样多个片段,都映射到同一个 sid。既解决长度问题,又是天然的数据增强。

def build_multiview_samples(doc, sid, n_views=4, win=256): samples = [] # 视角 1：标题 + 首段（最重要，权重最高） samples.append((f"索引文档: {doc.title} {doc.text[:win]}", sid)) # 视角 2：摘要（如果有） if doc.summary: samples.append((f"索引文档: {doc.summary}", sid)) # 视角 3~N：正文随机窗口 if len(doc.text) > win * 2: for _ in range(n_views - 2): start = random.randint(0, len(doc.text) - win) samples.append((f"索引文档: {doc.text[start:start+win]}", sid)) return samples

效果:模型学到"这篇 doc 的任何一个片段都指向同一个 sid",鲁棒性显著提升。 对长文档尤其重要,因为用户 query 可能命中文档任何位置的内容。

注意:视角 1(标题+首段)的采样权重应该更高(2~3 倍),它的信息密度最大。

方案三:Doc2Query 替代原文(NCI 的做法)

不喂原文,喂 LLM 生成的伪 query。

# 离线：每篇 doc 生成 10~20 个伪 query（覆盖不同段落的内容） pseudo_queries = generate_queries_from_doc(doc, n=15, cover_all_sections=True) # 训练样本 for pq in pseudo_queries: samples.append((f"检索: {pq}", sid))

优势:

  • 彻底绕开长度问题(query 都很短)
  • 训练/推理的输入分布一致(都是 query 形态),这是最大的好处
  • NCI 论文证明这比直接 indexing 效果更好

关键:生成伪 query 时要覆盖文档各个段落,不要只基于开头。

PROMPT = """阅读以下文档的各个部分，为每个主要内容点生成 1 个用户可能的搜索查询。 要求覆盖文档的不同章节，不要只关注开头。 文档：{doc_chunks} 查询列表："""

成本:长文档要分段喂给 LLM,离线生成成本较高。但这是一次性的。

方案四:结构化压缩

用规则/小模型把长文档压成信息密度高的短表示:

def compress_doc(doc, target_len=300): parts = [ doc.title, # 标题 doc.summary or first_sentence(doc), # 摘要或首句 " ".join(extract_keywords(doc, k=15)), # TextRank 关键词 " ".join(extract_entities(doc)), # 实体 " ".join(get_section_headers(doc)), # 小标题（长文档通常有） ] return " | ".join(p for p in parts if p)[:target_len]

小标题(section headers)是长文档的宝藏 —— 它们是人工写的内容摘要,信息密度极高,很多实现忽略了。

方案五:重新审视粒度 —— 一个 doc 是否应该只有一个 sid?

这是更深层的问题。如果你的 doc 很长且多主题(比如一篇综述、一份长报告), 用单个 sid 表示整篇文档本身就不合理:

  • d2d 向量是全文的平均 → 语义被"稀释"成一个模糊的中心点
  • 用户 query 命中的是其中某一节 → 但 sid 代表的是整篇的平均语义 → 必然不准

解决方案:chunk-level sid

# 一个 doc → 多个 chunk → 多个 sid for chunk in split_doc(doc, size=512, overlap=64): chunk_vec = d2d_encoder(chunk) chunk_sid = rq_fsq_quantize(chunk_vec) samples.append((f"索引文档: {chunk.text}", chunk_sid)) # 输入侧任务也基于 chunk samples.append((f"解码语义ID对应的内容摘要: {chunk_sid}", chunk.summary)) # 召回时：sid → chunk → 回溯到 doc，同 doc 多 chunk 命中则聚合加分

判断是否需要 chunk-level:

场景建议
doc < 1000 字,单主题doc-level sid,first-k 截断即可
doc 1000~3000 字,主题较集中doc-level + 多视角片段
doc > 3000 字,或明显多主题chunk-level sid
用户 query 常常只命中文档某一节chunk-level sid

代价是 sid 总量膨胀(码本压力)、需要 chunk→doc 的回溯聚合逻辑。 但对长文档场景,这通常是唯一正确的做法。

推荐组合
