1LLM 推理基础（小白必修）

一切推理框架的优化，都围绕本章四个概念展开：两阶段生成、KV Cache、显存墙、延迟指标。读懂本章，后面 80% 的参数调优都会有"原来如此"的感觉。

难度：入门理论 · 约 15 分钟

1.1 大模型推理在做什么？

大语言模型（LLM）本质是一个「文字接龙机」：给定前文，预测下一个 token（可以近似理解为"词/字"）的概率分布。所谓生成一段 100 字的回答，其实是模型循环执行了 100 次"预测下一个 token"的过程，每生成一个 token 都要完整跑一遍模型前向计算。

这带来推理服务区别于普通 Web 服务的三个核心事实：

🔁
自回归循环

输出一个 token 才能算下一个，生成 1000 token 就是 1000 次串行前向计算，天然无法并行。

🧮
矩阵乘密集

每一步都是数 GB 权重的矩阵乘法，算力受 GPU 限制，显存带宽往往是真正的瓶颈。

💾
中间结果巨大

每步计算产生的注意力中间量（KV Cache）必须留存，显存消耗随上下文长度线性增长。

1.2 Prefill 与 Decode：一次请求的两个阶段

把「输入一段 prompt、输出一段回答」拆开看，可以分为两个性质完全不同的阶段——这是理解所有推理框架的钥匙：

🟠 Prefill：读题
  • 输入 prompt 的所有 token 一次性并行计算（GPU 矩阵乘法的大批量运算，效率高）
  • 产出两样东西：第一个输出 token + 整个输入的 KV Cache
  • 输入越长，这一步越慢 → 直接决定用户等第一句话的时间
🟣 Decode：逐字作答
  • 每步只处理 1 个 token，串行循环直到输出结束符
  • 每步都要读完整份权重和 KV Cache → 显存带宽是瓶颈，GPU 算力反而空闲
  • 这正是"批处理"能提升吞吐的原因：多请求共享一次权重读取

1.3 KV Cache：显存的大头

KV Cache 是推理框架存在的根本理由。自回归生成时，每生成一个新 token 都要对"全部历史 token"做注意力计算。如果每一步都重算所有历史 token 的中间结果，成本是灾难性的；所以推理系统把每个 token 在每层的 Key、Value 向量缓存下来，这就是 KV Cache。

代价是显存。KV Cache 大小有精确公式：

公式
KV Cache 显存 ≈ 2 (K+V) × 层数 × KV 头数 × 每头维度 × 数据类型字节数 × 序列长度 × 并发请求数

用一个经典例子感受量级（7B 稠密模型、FP16 存储、32 层 / 32 头 / 每头 128 维）：

计算
单 token KV Cache = 2 × 32 × 32 × 128 × 2 bytes = 524,288 B ≈ 0.5 MB/token

→ 4096 token 上下文 ≈ 2 GB
→ 100 个并发请求 × 4K 上下文 ≈ 200 GB # 远超单卡显存！
注意现代大模型普遍使用 GQA（分组查询注意力）减少 KV 头数，实际占用比上例小很多，但量级规律不变：上下文越长、并发越多，KV Cache 越大。模型权重是固定的，KV Cache 才是显存的"动态大头"，也是框架调度的核心对象。具体数值请以模型 config.json 中的 num_hidden_layers、num_key_value_heads、head_dim 为准。

1.4 显存墙：一张卡到底能跑什么

部署一个模型前，先做一道小学数学题——显存分配。一块 GPU 的显存大致分成三块：

估算
总显存 = 模型权重 + KV Cache（预留池） + 激活值/框架开销

例：FP16 的 8B 模型 权重 ≈ 16 GB
    FP8  的 35B 模型 权重 ≈ 35 GB（MoE，总参 35B）
    剩余显存全部交给框架 → 划分为 KV Cache 池，决定能服务多少并发/多长上下文

由此得出三条部署铁律：

⚖️
权重是地板

权重装不下就是装不下，只能量化（FP8/INT4）或多卡切分（张量并行）。

🏊
KV 池是弹性空间

权重装下后，剩余显存由框架预分配为 KV Cache 池——池子越大，能扛的并发和上下文越大。

📉
量化一举两得

权重从 FP16 → FP8，权重减半、KV Cache 也减半（同样可量化），并发容量近乎翻倍。

小白提示记住经验法则：FP16 权重显存(GB) ≈ 参数量(B) × 2；FP8 则 ×1。例如 35B 模型 FP16 约 70GB（单张 96GB 的 H20 勉强），FP8 约 35GB（轻松装下，还剩约 55GB 给 KV Cache 和并发）。

1.5 性能指标：TTFT / TPOT / ITL / 吞吐

评价推理服务好坏，业界统一用四个指标（第 6 章压测时会反复出现）：

指标全称含义由什么阶段决定用户感受
TTFTTime To First Token发出请求到收到第一个 token 的时间Prefill 耗时 + 排队时间"多久开始吐字"
TPOTTime Per Output Token首字之后平均每 token 的耗时Decode 单步速度"吐字顺不顺"
ITLInter-Token Latency相邻两个 token 之间的延迟（逐次测量）Decode 单步速度"流式输出卡不卡"
吞吐Throughput每秒处理的总 token 数（全服务）批处理效率"这台机器值多少钱"
核心矛盾对话场景关心 低 TTFT + 稳定 ITL（交互体验），离线批处理关心 最大化吞吐（成本效率）。两者会互相牵制：塞进批次的请求越多吞吐越高，但单个请求被拖慢。vLLM 的全部调度艺术，就是在两者之间找平衡。

2vLLM 是什么：定位与整体架构

一句话：vLLM（virtual LLM，源自 UC Berkeley Sky 计算实验室）是一个高吞吐、显存高效的大模型推理与服务引擎——凭借 PagedAttention 成为社区生态最广的推理框架，也是很多人部署开源模型的默认起点。

难度：入门理论 · 约 10 分钟

2.1 为什么需要推理框架？

直接用 HuggingFace Transformers 起一个模型当然能跑，但一旦面对「多个用户同时请求」就立刻暴露三个问题：

排队浪费
逐请求串行执行，GPU 在等第一个请求结束，其余请求全部干等
→
显存碎片
按"最长上下文"整块预留 KV 显存，内部碎片 + 外部碎片严重，跑不了几个并发
→
重复计算
相同系统提示词被反复请求，每次都从头计算相同的 Prefill

vLLM 正是为解决这三件事而生，其中显存碎片问题是它的"立身之本"——2023 年论文《Efficient Memory Management for LLM Serving with PagedAttention》（SOSP 2023）给出的答案是：把操作系统管理内存的分页（Paging）思想搬进 KV Cache 管理。

2.2 vLLM 简史与实力

vLLM 于 2023 年 6 月开源，论文实测相比当时最先进的 FasterTransformer、Orca 等系统取得 2~4 倍吞吐（序列越长、模型越大、解码算法越复杂，优势越明显）。此后它成为社区事实标准之一：模型支持面最广、功能最全（多模态、LoRA、量化、投机解码、分布式），被大量生产平台采用。2025 年 1 月发布的 V1 架构完成了核心重构：调度器、KV 缓存管理器、工作器、采样器全部重写，追求"零配置 + 近零调度开销"，如今 V1 已在所有受支持场景默认启用。

2.3 整体架构：三层看懂 vLLM

你在命令行敲的参数（第 6 章），几乎都在影响这三层的行为：API 层决定"能不能接"，调度与缓存层决定"跑多快、装多少"，执行层决定"单个请求算多快"。

2.4 V0 → V1：新一代架构演进

V1 是理解当前 vLLM 行为的关键（很多老教程的参数在 V1 里已经变味或失效），核心变化一张表说清：

维度V0（旧）V1（现行默认）
代码结构新功能独立叠加，技术债累积模块化重构：调度器、KV 管理器、Worker、采样器重写
调度器预填充/解码分开调度，逻辑复杂零开销统一调度器：token 预算制，预填充与解码一视同仁
前缀缓存需 --enable-prefix-caching 手动开启默认开启（hash 去重 + LRU 驱逐）
分块预填充需 --enable-chunked-prefill 手动开启默认开启
LoRA / 投机解码开关多、组合复杂默认优化就绪，配置大幅简化

回退方式—环境变量 VLLM_USE_V1=0（仅排障时用）
为什么重要网上大量 2024 年的 vLLM 教程还在教"手动开启 prefix caching / chunked prefill"，在 V1 里这些参数默认已开；反过来，V1 也砍掉了一些老用法（如按请求 logits 处理器）。看教程时先确认它针对的版本，避免"参数配了没效果"或"行为对不上"。

2.5 一个请求的生命周期

请求到达

API Server 校验请求（含 API Key），Tokenizer 将文本切分为 token id 序列，注册到引擎的等待队列。

入队与预算分配

V1 统一调度器按 token 预算（受 KV 池容量约束）决定该请求何时进入运行批次；FCFS 或优先级排序。

KV 分页分配

KV 管理器从空闲 Block 池中按需分配显存页，并写入 Block Table（逻辑块 → 物理块映射）；命中前缀缓存的块直接复用。

GPU 执行

Prefill 批次一次性计算产出首 token；此后每个 Decode 步，批内所有请求各吐出一个 token，Block 逐个增长。

释放与响应

请求完成后 Block 归还池中；相同前缀的块因引用计数存在而保留（Copy-on-Write 保护），流式响应逐 token 推给客户端。

与 SGLang 的差别vLLM 的缓存以"块哈希 + LRU"为核心，SGLang 以"基数树"为核心——两者都实现前缀复用，数据组织方式不同（第 3.1、3.3 节会展开）。理解这一点后，两份报告可以互相印证。

3核心技术原理：vLLM 为什么快

本章拆解 vLLM 的六板斧：PagedAttention、Continuous Batching、前缀缓存、分块预填充、量化、投机解码。每一项都对应一个"痛点 → 思路 → 效果"的故事。

难度：入门 → 进阶理论 · 约 20 分钟

3.1 PagedAttention：像操作系统管理内存一样管理 KV Cache vLLM 招牌

痛点：传统方案给每个请求按"模型最大上下文长度"整块预留连续显存（比如预留 4096 token 的位置）。但实际请求往往只用几百 token——论文实测这种方式的显存浪费率高达 60%~80%：请求之间留缝隙（外部碎片）、预留但没用满（内部碎片），宝贵的显存被白白锁死，并发上不去。

思路：借鉴操作系统虚拟内存的分页机制。把 KV Cache 切成固定大小的块（Block，如 16 个 token 一块），按需分配；请求内部维护一张Block Table（块表）记录"逻辑块 → 物理块"的映射——逻辑上连续，物理上可以东一块西一块，就像硬盘的簇。

这带来三重收益：

🧩
近零显存浪费

按需分配块，碎片率从 60~80% 降到近零 → 同样显存能塞下更多并发，这是 2~4× 吞吐的直接来源。

🤝
块共享

相同前缀的块被多个请求引用同一份物理块（引用计数 + Copy-on-Write），省显存又省计算。

🔀
灵活解码

束搜索（beam search）、并行采样等多分支输出共享大部分块，复杂解码算法不再"倍增显存"。

一句话记住 PagedAttention操作系统当年用分页解决了内存碎片，vLLM 把同一招搬到 KV Cache 上——"虚拟内存 for KV Cache"。块大小（--block-size，默认 16 token）越小越灵活，元数据开销略增。

3.2 Continuous Batching：别让 GPU 等最后一个字

痛点（静态批处理）：把一批请求拼在一起跑完再接下一批。但批内各请求输出长度差异巨大——第一个请求生成 10 个 token 就结束了，却必须陪着生成 1000 个 token 的请求跑完全程，GPU 大量算力被"陪跑"浪费。

思路：调度器在每个 Decode 步之后重新审视批次——已完成的请求立刻移出，其 Block 归还，等待队列的新请求立刻补位。vLLM 的迭代级调度（iteration-level scheduling）正是这一思想的代表实现。

3.3 前缀缓存（Prefix Caching）：相同开头只算一次

真实业务中大量请求共享前缀——同一个系统提示词、同一段 Few-shot 示例、同一个 RAG 文档。vLLM 的做法：给每个 KV 块计算哈希（内容相同则哈希相同），新请求的 prompt 按块切分后逐块查表，命中则直接复用物理块，只对"分叉之后"的新增部分做 Prefill。缓存池按 LRU（最近最少使用）驱逐。

vLLM：哈希 + LRU
  • 每块 KV 按内容哈希索引，O(1) 查找
  • V1 中默认开启，无需任何参数
  • 实现简单、通用；多请求同前缀场景收益显著
SGLang：基数树（对比记忆）
  • 用 RadixTree 组织前缀，天然表达"树状分叉"结构
  • 支持逐层驱逐与更精细的复用
  • 两者收益场景高度重叠，实现哲学不同
进阶：缓存命中如何被调度利用调度器会感知缓存状态——长前缀请求命中缓存后 Prefill 几乎免费，TTFT 大幅下降。可以用 --no-enable-prefix-caching 关闭它（如提示词 logprobs 场景），或用 --enable-prefix-caching 显式确认（V1 默认已是开启状态）。

3.4 分块预填充（Chunked Prefill）

痛点：一个 32K 长输入的 Prefill 是一次超大计算，执行期间整个 GPU 被"霸占"，同批正在 Decode 的请求全部停摆——用户看到的就是"第一句话出来后突然卡住"。

思路：把长 Prefill 切成固定 token 预算的块（--max-num-batched-tokens 控制，如 8192），每步只算一块，块与块之间穿插执行其他请求的 Decode。V1 的统一调度器走得更远：不再显式区分"预填充步"和"解码步"，一个混合批次里同时有"某请求的下一个预填充块"和"其他请求的 decode"，token 预算统一分配——这就是"零开销统一调度器"的含义。

调优含义预算越大 → Prefill 越快（TTFT 更好）但瞬时显存占用越高；预算越小 → 越平滑但总时长略增。长 prompt 场景遇到 Prefill OOM 或 TTFT 抖动，第一反应就是调 --max-num-batched-tokens。

3.5 量化：FP8 / INT4 / AWQ / GPTQ

量化 = 用更少的比特存储权重（以及可选的 KV Cache），换来显存减半甚至更多、带宽压力更小、吞吐更高，代价是可能有轻微精度损失（必须用基准任务验证）。vLLM 的量化生态是各家框架里最全的之一：

方案精度典型来源硬件要求（要点）
FP8 (W8A8)8bit 浮点官方 FP8 模型 / LLM CompressorAda / Hopper（SM89+），H20 ✔
INT4 (W4A16)4bit 权重LLM Compressor / GPTQ / AWQAmpere 起；Marlin 内核加速
GPTQ4bit 权重GPTQModel 离线量化Ampere 起
AWQ4bit 权重AutoAWQ 离线量化Ampere 起（Turing 部分支持）
BitsAndBytes8/4bit即插即用兼容性好，性能一般
GGUF多种llama.cpp 生态模型兼容性最广

加载规则：已量化模型（AWQ/GPTQ/FP8 官方版）直接加载，vLLM 会自动从模型目录的量化配置识别方案，无需加 --quantization；只有加载未量化权重并希望现场量化（在线量化，如 --quantization fp8）时才需要指定。官方推荐的量化工具链是 LLM Compressor（支持 FP8 W8A8、INT4 W4A16 等方案）。另一根杠杆是 KV Cache 量化：--kv-cache-dtype fp8 让 KV 池容量近乎翻倍（Hopper 上 V1 已支持）。

3.6 投机解码（Speculative Decoding）

Decode 串行慢的本质是"一步只验证一个 token"。投机解码用一个小而快的草稿模型（或 n-gram / MLP 草稿器）连续猜 K 个 token，再让大模型一次前向并行验证——猜中的部分等于"一步生成多个 token"，输出分布与原模型保持一致。V1 中投机解码已默认优化就绪，常用形态：

bashspec_decode.sh
# n-gram 草稿（无需额外模型，对重复文本/代码场景友好）
vllm serve meta-llama/Llama-3.1-8B-Instruct --speculative-config '{"method":"ngram","prompt_lookup_max":4}'

# 草稿模型（EAGLE / 普通小模型）
vllm serve meta-llama/Llama-3.1-8B-Instruct \
    --speculative-config '{"method":"eagle","model":"yuhuili/EAGLE-LLaMA3.1-8B"}'
注意投机解码的收益取决于接受率：草稿猜得准才加速，猜不准反而浪费算力。建议先跑通基线，再在自己的负载上 A/B 验证（文本重复度高、代码、JSON 输出等场景接受率通常更高）。

3.7 并行策略：单卡放不下怎么办

策略参数原理适用
张量并行 TP--tensor-parallel-size N把每一层的权重矩阵横向切开分到 N 张卡，各卡算一部分再通信合并权重单卡装不下；省显存为主，卡间需高带宽互联
流水线并行 PP--pipeline-parallel-size N把模型的层纵向分段，各卡负责一段，请求像流水线一样流过跨机带宽差时比 TP 友好；与 TP 组合
数据并行 DP--data-parallel-size N起 N 个引擎副本，各自服务不同请求追求吞吐；多机部署常用外置负载均衡或内置 DP
专家并行 EP--enable-expert-parallelMoE 模型的"专家"分散到多卡MoE 模型（DeepSeek、Qwen-A3B 系列）专家表过大时
官方口径TP 的首要目的是省显存而非提速；显存够用时，多副本（DP）对吞吐更友好。中小规模部署优先想清楚"权重 + KV 池"到底需要几张卡，再决定 TP/DP 组合。

3.8 结构化输出（Structured Outputs）

让模型"必须输出合法 JSON / 必须匹配某个正则 / 必须从固定选项中选一个"是工程化落地的刚需。vLLM 的做法同样是约束解码：把目标格式编译成状态机，Decode 每一步只允许采样"当前状态下合法的 token"。后端支持 xgrammar（默认自动选择）与 guidance；提示：v0.12.0 起 guided_json 等旧字段已移除，统一迁移到 structured_outputs 写法（实战见第 5.6 节）。

5.2 离线批量推理：LLM 类（不启动服务直接跑）

如果你只是要离线处理一批文本（数据清洗、打标、评测），用 vllm.LLM 类最直接：

from vllm import LLM, SamplingParams

prompts = [
    "Hello, my name is",
    "The president of the United States is",
    "The capital of France is",
    "The future of AI is",
]
# 采样参数（温度、top_p 等）

# 初始化引擎：首次运行自动从 HuggingFace 下载模型

outputs = llm.generate(prompts, sampling_params)
for output in outputs:
    print(f"Prompt: {output.prompt!r}")
    print(f"生成  : {output.outputs[0].text!r}\n")
注意：generate 不会套聊天模板llm.generate 是裸文本补全。对 Instruct/Chat 模型要么手动套 chat template，要么直接用 llm.chat(messages)（自动应用模板）：

5.5 结构化输出实战：让模型 100% 输出合法 JSON

JSON Schema + Pydantic（推荐姿势）

pythonjson_output.py

from enum import Enum

    model: str
    car_type: CarType

choice / regex / grammar 约束（extra_body 新写法）

pythonconstraints.py

    model="Qwen/Qwen2.5-1.5B-Instruct",

6启动参数详解与性能调优

vLLM 的参数有数百个，但日常调优真正高频的只有十几个。本章给出速查表 + 调优决策树 + 压测方法，覆盖 90% 的实战需求。

难度：进阶动手 · 含压测命令

6.1 常用启动参数速查表

参数默认作用什么时候动它
--model—模型路径（本地目录或 HF 仓库 ID）必填
--tensor-parallel-size1张量并行卡数（TP），权重切分到 N 张卡单卡装不下权重时；目的是省显存而非提速
--pipeline-parallel-size1流水线并行（PP），按层切分跨机带宽受限时与 TP 组合
--data-parallel-size1数据并行副本数显存充足追求吞吐
--gpu-memory-utilization0.9允许 vLLM 占用的显存比例（权重+KV 池）OOM → 调小（如 0.8）；KV 池太小 → 调大
--max-model-len模型 config 值最大上下文长度最重要的显存杠杆：按业务实际需要调小（如 8192），可大幅扩大并发容量
--max-num-seqs自动最大并发序列数按业务 QPS 与显存设定
--max-num-batched-tokens自动每步调度的 token 预算（分块预填充粒度）长 prompt Prefill OOM → 调小；追求 TTFT → 调大
--block-size16PagedAttention 块大小（token/块）一般不动
--kv-cache-dtypeautoKV 缓存类型设 fp8 让 KV 池容量近乎翻倍
--quantization自动权重量化方式在线量化时用（如 fp8）；已量化模型自动识别，不要重复指定
--enable-prefix-cachingV1 已默认开前缀缓存仅 --no-enable-prefix-caching 关闭（提示词 logprobs 等场景）
--enable-chunked-prefillV1 已默认开分块预填充一般不动
--scheduling-policyfcfs调度策略可用 priority 优先级调度
--enable-lora关启用 LoRA 适配器服务多租户多风格模型场景
--speculative-config关投机解码配置（JSON）ngram/草稿模型加速，见 3.6 节
--api-key无API Key 鉴权公网/多租户服务建议开启
--reasoning-parser无推理模型思考内容解析（如 qwen3）推理型模型需要拆分思考/正文时
--attention-backend自动注意力内核（FLASH_ATTN / FLASHINFER）一般不动；FlashInfer 需单独安装
V1 版本陷阱老教程里"开启 prefix caching / chunked prefill"的参数在 V1 已默认生效；反过来，best_of、按请求 logits 处理器、GPU↔CPU KV 缓存交换已在 V1 移除。遇到"参数配了没反应"，先确认：教程的版本 vs 你装的版本（vllm --version）。

6.2 显存与调度调优决策树

bashdecision_tree.txt
启动失败/报错时按顺序排查：

CUDA out of memory（模型加载阶段）
  └─ 权重太大 → --tensor-parallel-size 加卡数，或换量化版本模型
CUDA out of memory（KV cache 分配阶段）
  └─ --gpu-memory-utilization 调小（如 0.8）→ 给激活值留出空间
     或 --max-model-len 调小（按业务真实需要，是最有效的并发扩容手段）
长 prompt Prefill 阶段 OOM / TTFT 抖动
  └─ --max-num-batched-tokens 调小（如 4096）
并发上不去
  └─ ① nvidia-smi 看 KV 池占用是否吃满 → 否则增大 --gpu-memory-utilization
     ② --max-model-len 是否设得过大（按业务需要收敛）
     ③ 量化：--kv-cache-dtype fp8 让池容量翻倍
吞吐不达标
  └─ ① 确认 prefix caching 生效（重复前缀场景）
     ② vllm bench serve 逐级上调 --max-concurrency 找拐点
     ③ 显存富余 → 考虑 --data-parallel-size 多副本
显存占用哲学vLLM 会"贪婪"地预分配 KV 池（占满 --gpu-memory-utilization 允许的部分），这是特性不是 bug——空着也是浪费。如果你要在同一张卡上跑别的进程，请务必调低 --gpu-memory-utilization，否则互相 OOM。

调优前后必须用数据说话。vLLM 自带端到端压测工具 vllm bench serve（模拟真实用户走 HTTP，测的是"包含网络栈"的服务性能）：

关键项含义调优含义

7实战：部署 Qwen3.6-35B-A3B-FP8（含鲁班 GPU 环境适配）

本章把前六章的知识全部串起来：在鲁班（Luban ML）平台的 H20 GPU 环境中，用 vLLM 部署你本地已下载的 Qwen/Qwen3.6-35B-A3B-FP8（MoE，总参 35B / 激活 3B，约 35GB，支持 262K 上下文）——这正是该模型官方给出的推荐部署方案（vllm>=0.19.0）。

难度：进阶动手实战环境：鲁班平台 · H20 · ceph 存储

7.1 认识部署对象：MoE + FP8 意味着什么

🧩
MoE：35B 参数，3B 激活

总参数 35B 决定显存下限（权重都要装下），每 token 仅激活 3B 决定计算量小——Decode 快、吞吐高，是"显存贵、算力富余"的典型画像。

🗜️
FP8 官方量化

权重约 35GB（FP16 版要 70GB），细粒度 block=128 量化，质量与 BF16 几乎一致。vLLM 可直接加载，无需再加 --quantization 参数（FP8 需 Ada/Hopper 架构，H20 ✔）。

📏
262K 超长上下文

上下文上限 262144 token。KV Cache 随上下文线性膨胀——服务真实长文本时，--max-model-len 与 KV 池容量需要一起权衡。

🎛️
EP 专家并行可选

MoE 的专家可切分到多卡（--enable-expert-parallel）。多卡部署时在"纯 TP"与"TP+EP"之间选择，大专家表时 EP 更省显存通信。

7.2 硬件规划：需要几张 H20？

鲁班平台 GPU 环境以 NVIDIA H20（96GB HBM3）为主。做一遍第 1.4 节的显存账：

估算h20_planning.txt
权重（FP8）                ≈ 35 GB
激活值/框架开销（预留）     ≈ 5 ~ 8 GB
可用于 KV Cache 池（--gpu-memory-utilization=0.9 时）

单卡 H20 = 96 GB：
  tp=2：每卡权重 17.5GB，两卡共 ≈ 130GB KV 池 → 8~32K 上下文常规服务首选
  tp=4：每卡权重 8.75GB，KV 池极大 → 262K 长上下文 & 高并发压测首选
  tp=8：模型官方推荐档位（262K 满上下文 + 大并发的保守配置）

结论：
  · 功能验证（8K 上下文）    → 1~2×H20 即可起步
  · 常规服务（8~32K 上下文） → 2~4×H20
  · 满血 262K 上下文生产服务 → 4~8×H20（官方推荐 tp=8）
为什么推荐 tp=4 起步H20 是显存大、带宽相对受限的卡型：MoE + FP8 下 Decode 计算压力不大，瓶颈更偏显存容量与带宽——多切几份权重（TP）能让每卡的 KV 池和带宽压力都下降，对 262K 长上下文的"载重"场景收益直接。鲁班训练资源参考：30B~40B 模型对应 32 卡训练（微调场景），而推理部署只需其中一小部分卡。

7.3 部署命令（单机多卡）

模型已位于 ceph 路径 …/user_yateschen/qwen/Qwen3.6-35B-A3B-FP8，直接用本地路径启动。以下即该模型官方推荐的 vLLM 命令（本地路径 + 按需调整 tp）：

bashserve_qwen35b.sh
export MODEL_DIR=/mnt/gemininjceph7/geminicephfs/mmsearch-luban-universal/group_2/sg1/user_yateschen/qwen/Qwen3.6-35B-A3B-FP8

# 官方推荐档：8 卡 TP，262K 满上下文，推理模型解析
vllm serve $MODEL_DIR \
    --host 0.0.0.0 --port 8000 \
    --tensor-parallel-size 8 \
    --max-model-len 262144 \
    --reasoning-parser qwen3

常用变体：

bashvariants.sh
# 变体 1：4 卡起步（常规上下文服务，KV 池富余）
vllm serve $MODEL_DIR --tensor-parallel-size 4 --max-model-len 32768 --port 8000

# 变体 2：KV Cache 也用 FP8（池容量近乎翻倍）
vllm serve $MODEL_DIR --tensor-parallel-size 4 --max-model-len 32768 \
    --kv-cache-dtype fp8 --port 8000

# 变体 3：MoE 专家并行 + 限制并发保护延迟
vllm serve $MODEL_DIR --tensor-parallel-size 4 --enable-expert-parallel \
    --max-model-len 65536 --max-num-seqs 128 --port 8000

# 变体 4：多轮对话场景确认前缀缓存（V1 默认开启，显式写出仅为可读性）
vllm serve $MODEL_DIR --tensor-parallel-size 4 --enable-prefix-caching --port 8000
踩坑：不要画蛇添足FP8 版模型已量化，启动命令中不要加 --quantization fp8——vLLM 会从模型 config 自动识别，重复指定反而可能走错内核。--reasoning-parser qwen3 只在模型是"推理型"（输出含思考过程）时需要，普通对话模型不用加。

8常见问题排查（FAQ）

按"症状 → 处方"组织，覆盖安装、启动、运行三个阶段的高频问题。

难度：入门排错手册
启动阶段：CUDA out of memory

区分两种 OOM：加载权重阶段 OOM → 权重太大，加 --tensor-parallel-size 卡数或换量化版模型；KV cache 分配阶段 OOM → 调小 --gpu-memory-utilization（如 0.8），给激活值和框架开销留空间；同时检查 --max-model-len 是否远超业务需要（它是 KV 池压力的最大变量）。

vLLM 把显存全占了，同卡还要跑别的进程

这是 vLLM 的贪婪预分配设计（特性不是 bug）：启动时按 --gpu-memory-utilization（默认 0.9）占满可用显存做 KV 池。同卡多进程请调低该参数，或干脆用多卡分离部署。

参数配了没反应：prefix caching / chunked prefill

V1 中两者默认开启，无需手动开。老教程（V0 时代）的写法在现代版本中要么已默认、要么已废弃。先用 vllm --version 确认版本，再对照本报告 2.4 节的 V1 变化表。

报错：guided_json / guided_regex 参数不存在

v0.12.0 起 guided_* 字段已移除，迁移到 extra_body={"structured_outputs": {"json": ...}} 等新写法（见 5.5 节对照表）。

llm.generate 输出是乱码/不像对话

llm.generate 是裸补全，不会应用聊天模板。对 Instruct/Chat 模型请改用 llm.chat(messages)，或走 vllm serve 的 chat 接口。

采样参数和我设置的不一样

vLLM 默认读取模型仓库的 generation_config.json（Qwen 等官方模型常内置推荐参数）。想强制 vLLM 默认值：LLM(model=..., generation_config="vllm") 或 serve 时 --generation-config vllm。

长 prompt 推理时 OOM / TTFT 突然变高

调小 --max-num-batched-tokens（如 4096）让分块预填充更细；或降低 --max-model-len；并发过载时下调 --max-num-seqs 保护在线体验。

模型从 HuggingFace 下载失败 / 很慢

国内环境先 export HF_ENDPOINT=https://hf-mirror.com；gated 模型设置 HF_TOKEN；也可用 ModelScope：export VLLM_USE_MODELSCOPE=True。生产环境最佳实践：在能联网的机器上把权重整仓下载到 ceph/共享盘（参考第 7 章），服务端只引用本地路径。

加载 FP8/AWQ/GPTQ 模型后要不要加 --quantization？

不要。预量化模型从模型目录的量化配置自动识别，重复指定可能选择错误内核。只有加载 FP16/BF16 原版并希望现场量化时才加（如 --quantization fp8，要求 Ada/Hopper 架构）。

FP8 模型报硬件不支持

FP8 (W8A8) 需要 Ada（SM89）/ Hopper（SM90）及以上架构（A100 不支持 FP8，可用 INT8 W8A8 或 INT4 替代）。H20/H100/L20/L40S 均支持。

吞吐远低于预期

按顺序检查：① 前缀缓存是否开启、重复前缀是否命中（日志 cached tokens）；② vllm bench serve 逐级上调 --max-concurrency 找拐点；③ 显存富余时上 --kv-cache-dtype fp8 或 --data-parallel-size 多副本；④ 高重复文本可试验 --speculative-config ngram 投机解码。

V1 不支持我的模型（编码器-解码器 / Mamba-1）

V1 暂缓了部分架构（Bart、Mllama 等编码器-解码器；Mamba-1；混合架构需禁用前缀缓存）。临时回退 V0：export VLLM_USE_V1=0，或升级版本/关注模型支持列表。

bench 全部请求失败 / 401、403

核对 --backend 与端点、--base-url、--model 是否与服务端一致；服务端开了 --api-key 时压测也要带同样的 key。
