1LLM 推理基础（小白必修）

一切推理框架的优化，都围绕本章这四个概念展开：两阶段生成、KV Cache、显存墙、延迟指标。读懂本章，后面 80% 的参数调优都会有"原来如此"的感觉。

难度：入门理论 · 约 15 分钟

1.1 大模型推理在做什么？

大语言模型（LLM）本质是一个「文字接龙机」：给定前文，预测下一个 token（可以近似理解为"词/字"）的概率分布。所谓生成一段 100 字的回答，其实是模型循环执行了 100 次"预测下一个 token"的过程，每生成一个 token 都要完整跑一遍模型前向计算。

这带来推理服务区别于普通 Web 服务的三个核心事实：

🔁
自回归循环

输出一个 token 才能算下一个，生成 1000 token 就是 1000 次串行前向计算，天然无法并行。

🧮
矩阵乘密集

每一步都是数 GB 权重的矩阵乘法，算力受 GPU 限制，显存带宽往往是真正的瓶颈。

💾
中间结果巨大

每一步计算产生的注意力中间量（KV Cache）必须留存，显存消耗随上下文长度线性增长。

1.2 Prefill 与 Decode：一次请求的两个阶段

把「输入一段 prompt、输出一段回答」拆开看，可以分为两个性质完全不同的阶段——这是理解所有推理框架的钥匙：

🔵 Prefill：读题
  • 输入 prompt 的所有 token 一次性并行计算（GPU 矩阵乘法的大批量运算，效率高）
  • 产出两样东西：第一个输出 token + 整个输入的 KV Cache
  • 输入越长，这一步越慢 → 直接决定用户等第一句话的时间
🟣 Decode：逐字作答
  • 每步只处理 1 个 token，串行循环直到输出结束符
  • 每步都要读完整份权重和 KV Cache → 显存带宽是瓶颈，GPU 算力反而空闲
  • 这正是"批处理"能提升吞吐的原因：多请求共享一次权重读取

1.3 KV Cache：显存的大头

KV Cache 是推理框架存在的根本理由。自回归生成时，每生成一个新 token 都要对"全部历史 token"做注意力计算。如果每一步都重算所有历史 token 的中间结果，成本是灾难性的；所以推理系统把每个 token 在每层的 Key、Value 向量缓存下来，这就是 KV Cache。

代价是显存。KV Cache 大小有精确公式：

公式
KV Cache 显存 ≈ 2 (K+V) × 层数 × KV 头数 × 每头维度 × 数据类型字节数 × 序列长度 × 并发请求数

用一个经典例子感受量级（7B 稠密模型、FP16 存储、32 层 / 32 头 / 每头 128 维）：

计算
单 token KV Cache = 2 × 32 × 32 × 128 × 2 bytes = 524,288 B ≈ 0.5 MB/token

→ 4096 token 上下文 ≈ 2 GB
→ 100 个并发请求 × 4K 上下文 ≈ 200 GB # 远超单卡显存！
注意现代大模型普遍使用 GQA（分组查询注意力）减少 KV 头数，实际占用比上例小很多，但量级规律不变：上下文越长、并发越多，KV Cache 越大。模型权重是固定的，KV Cache 才是显存的"动态大头"，也是框架调度的核心对象。具体数值请以模型 config.json 中的 num_hidden_layers、num_key_value_heads、head_dim 为准。

1.4 显存墙：一张卡到底能跑什么

部署一个模型前，先做一道小学数学题——显存分配。一块 GPU 的显存大致分成三块：

估算
总显存 = 模型权重 + KV Cache（预留池） + 激活值/框架开销

例：FP16 的 8B 模型 权重 ≈ 16 GB
    FP8  的 35B 模型 权重 ≈ 35 GB（MoE，总参 35B）
    剩余显存全部交给框架 → 划分为 KV Cache 池，决定能服务多少并发/多长上下文

由此得出三条部署铁律：

⚖️
权重是地板

权重装不下就是装不下，只能量化（FP8/INT4）或多卡切分（张量并行）。

🏊
KV 池是弹性空间

权重装下后，剩余显存由框架预分配为 KV Cache 池——池子越大，能扛的并发和上下文越大。

📉
量化一举两得

权重从 FP16 → FP8，权重减半、KV Cache 也减半（同样可量化），并发容量近乎翻倍。

小白提示记住经验法则：FP16 权重显存(GB) ≈ 参数量(B) × 2；FP8 则 ×1。例如 35B 模型 FP16 约 70GB（单张 96GB 的 H20 勉强），FP8 约 35GB（轻松装下，还剩约 55GB 给 KV Cache 和并发）。

1.5 性能指标：TTFT / TPOT / ITL / 吞吐

评价推理服务好坏，业界统一用四个指标（第 6 章压测时会反复出现）：

指标全称含义由什么阶段决定用户感受
TTFTTime To First Token发出请求到收到第一个 token 的时间Prefill 耗时 + 排队时间"多久开始吐字"
TPOTTime Per Output Token首字之后平均每 token 的耗时Decode 单步速度"吐字顺不顺"
ITLInter-Token Latency相邻两个 token 之间的延迟（逐次测量）Decode 单步速度"流式输出卡不卡"
吞吐Throughput每秒处理的总 token 数（全服务）批处理效率"这台机器值多少钱"
核心矛盾对话场景关心 低 TTFT + 稳定 ITL（交互体验），离线批处理关心 最大化吞吐（成本效率）。两者会互相牵制：塞进批次的请求越多吞吐越高，但单个请求被拖慢。推理框架的全部调度艺术，就是在两者之间找平衡。

2SGLang 是什么：定位与整体架构

一句话：SGLang（SG-Lang，源自 Stanford）是一个大模型与多模态模型的高性能推理服务框架——对外提供 OpenAI 兼容的 HTTP 服务，对内用一系列调度与缓存技术把 GPU 榨干。

难度：入门理论 · 约 10 分钟

2.1 为什么需要推理框架？

直接用 HuggingFace Transformers 起一个模型当然能跑，但一旦面对「多个用户同时请求」就立刻暴露三个问题：

排队浪费
逐请求串行执行，GPU 在等第一个请求结束，其余请求全部干等
→
重复计算
100 个请求共用同一个系统提示词，每个都从头计算相同的 Prefill
→
显存碎片
按"最长上下文"预留显存，实际利用率极低，跑不了几个并发

推理框架（SGLang / vLLM 等）就是为解决这三件事而生：调度器管理批次与显存，缓存系统消除重复计算，服务层封装 API。SGLang 在此之上还有一张王牌——RadixAttention 前缀缓存（第 3.1 节），以及一门可选的"结构化生成编程语言"（前端 DSL）。

2.2 SGLang 简史与实力

SGLang 由斯坦福团队的论文《SGLang: Efficient Execution of Structured Language Model Programs》（arXiv 2312.07104）提出，初始亮点是「前端 DSL + RadixAttention 缓存运行时」的协同设计：在各种复杂任务（多轮对话、Agent、JSON 输出、少样本学习）上，相比当时最先进的推理系统取得最高 6.4 倍吞吐。此后社区快速发展，如今被广泛用于大规模生产部署，尤其在 DeepSeek 等主流开源模型的推理上被官方推荐。它对硬件的适配面也很宽：NVIDIA sm80 以上 GPU（A10/A100/L40S/H100/H20…），并支持 AMD GPU、Intel CPU、TPU、昇腾 NPU 等。

2.3 整体架构：三层看懂 SGLang

三个层次各司其职：服务层把 HTTP 请求翻译成内部任务；调度与缓存层决定"哪些请求一起跑、KV Cache 放哪、哪些可以复用"；执行层负责把批次真正喂给 GPU。你在命令行敲的参数（第 6 章），几乎都在影响这三层的行为。

2.4 一个请求的生命周期

请求到达

HTTP 服务层校验请求，Tokenizer 将文本切分为 token id 序列，进入等待队列。

前缀匹配

RadixCache 在 KV Cache 树中查找该请求与历史请求的共同前缀，命中的部分直接复用，无需重算 Prefill（这是 SGLang 的招牌优势）。

组批调度

调度器按策略（默认 fcfs）把请求加入当前批次；Prefill 与 Decode 分开组批、分块执行，避免互相阻塞。

GPU 执行

执行层对 Prefill 批次做一次大矩阵计算（产出首 token），随后每个 Decode 步为批内所有请求各吐出一个 token，循环至各请求完成。

写回与响应

新产生的 KV Cache 挂到 RadixTree 上供后续请求复用；流式响应逐 token 推给客户端；请求结束后其缓存不删除，留在树中等待复用或按策略驱逐。

小白提示注意第 5 步：请求结束后 KV Cache 不立即释放，而是留在缓存树里。这是 SGLang 与很多框架最直观的差异——"缓存是资产，不是垃圾"。

3核心技术原理：SGLang 为什么快

本章拆解 SGLang 的六板斧：RadixAttention、HiCache、Continuous Batching、分块预填充、约束解码、并行与量化。每一项都对应一个"痛点 → 思路 → 效果"的故事。

难度：入门 → 进阶理论 · 约 20 分钟

3.1 RadixAttention：前缀缓存的王牌 SGLang 招牌

痛点：真实业务中大量请求共享前缀——同一个系统提示词、同一段Few-shot示例、同一个文档的 RAG 问答、同一个任务的多轮对话。传统框架在请求结束后丢弃 KV Cache，下个请求从头重算一遍完全相同的内容。

思路：把所有请求的 KV Cache 组织成一棵基数树（Radix Tree）。树的每条边是一段 token 序列，根到某节点的路径 = 某个请求的前缀。新请求到达时沿树匹配，共享前缀的 KV Cache 直接复用，只对"分叉之后"的新增部分做 Prefill。

效果与代价：命中前缀的部分 Prefill 时间趋近于零——对"固定系统提示词被成千上万次请求复用"的场景是数量级的加速；论文实测各种负载下最高 6.4× 吞吐。代价方面，命中率为 0 时树查询的额外开销可忽略，且它与其余加速手段（Continuous Batching、PagedAttention 式分页管理、张量并行）完全正交、默认开启。两处工程细节值得记住：

  • 缓存淘汰：显存不足时按 LRU（最近最少使用）从树中驱逐叶子节点的缓存段。
  • 配合调度：调度器有 prefix-aware 策略，会优先把"能复用缓存"的请求凑在一起组批，进一步提高命中率。
注意RadixAttention 只在单实例的 GPU 显存（L1）内复用。显存装不下超长历史怎么办？——引出下一节 HiCache。

3.2 HiCache：把前缀缓存扩展到 GPU 之外

HiCache 借鉴 CPU 三级缓存思想，把 KV Cache 组织成三级层级，专治"长上下文 + 多轮对话 + 集群多实例"下缓存放不下的问题：

层级介质可见范围类比
L1GPU 显存（HBM）单推理实例私有CPU 私有 L1 缓存
L2主机内存（CPU RAM）节点内单实例私有CPU 私有 L2 缓存
L3分布式存储后端（Mooncake / 3FS / 文件…）集群共享共享 L3 缓存

工作流围绕三个动作：本地匹配（沿 HiRadixTree 快速查 L1/L2，纯元数据遍历，极快）→ 预取（L3 命中超过阈值——默认 256 token——时异步搬回本地，支持 best_effort / wait_complete / timeout 三种策略，生产推荐 timeout）→ 写回（write_through 立即写 / write_through_selective 热点才写 / write_back 驱逐时写）。配合 GPU 辅助 I/O 内核与"计算第 N 层时预取第 N+1 层"的重叠设计，传输开销被大幅隐藏（内核方案最高 3 倍于基线拷贝）。

进阶：什么场景值得开 HiCache？多轮 Agent（历史逐轮增长且被反复请求）、超长文档 RAG（同一文档被大量问题命中）、多实例部署（L3 让全集群共享热点前缀）。随机短对话场景收益很小，默认关闭即可。开启方式见第 6 章参数表（--enable-hierarchical-cache）。

3.3 Continuous Batching：别让 GPU 等最后一个字

痛点（静态批处理）：把一批请求拼在一起跑完再接下一批。但批内各请求输出长度差异巨大——第一个请求生成 10 个 token 就结束了，却必须陪着生成 1000 个 token 的请求跑完全程，GPU 大量算力被"陪跑"浪费。

思路：调度器在每个 Decode 步之后重新审视批次——已完成的请求立刻移出，其显存释放，等待队列的新请求立刻补位。批次不再是"一次拼死"的静态组合，而是持续滚动换血。这是所有现代推理引擎的标配，SGLang 的特色在于它与 RadixAttention 前缀调度协同（优先插入能复用缓存的请求）。

3.4 分块预填充（Chunked Prefill）

痛点：一个 32K 长输入的 Prefill 是一次超大计算，执行期间整个 GPU 被"霸占"，同批正在 Decode 的请求全部停摆——用户看到的就是"第一句话出来后突然卡住"。

思路：把长 Prefill 切成固定大小的块（如 --chunked-prefill-size 8192），每步只算一块，块与块之间穿插执行其他请求的 Decode。长请求的 Prefill 不再阻塞别人，TTFT 与 ITL 的抖动显著减小。

调优含义块越大 → Prefill 越快（TTFT 更好）但瞬时显存占用越高；块越小 → 越平滑但总时长略增。长 prompt 场景遇到 Prefill OOM，第一反应就是调小 --chunked-prefill-size（如 4096）。

3.5 结构化输出：约束解码与压缩 FSM

让模型"必须输出合法 JSON / 必须匹配某个正则 / 必须从固定选项中选一个"，是 Agent 与工程化落地的刚需。SGLang 的做法是约束解码：把目标格式（JSON Schema、正则、EBNF 文法）编译成一个有限状态机（FSM），Decode 的每一步只允许模型从"当前状态下合法的 token"中采样——输出100% 语法合法，不需要靠提示词乞求模型听话。

SGLang 的优化点是压缩 FSM：论文指出传统方法对每个 token 单独建 FSM 状态、开销大，SGLang 将 FSM 压缩合并状态、复用转移，让约束解码几乎不拖慢速度。默认后端为 XGrammar（也可切换 Outlines / llguidance）。工程用法见第 5.6 节。

3.6 并行策略：单卡放不下怎么办

策略参数原理适用
张量并行 TP--tp N把每一层的权重矩阵横向切开分到 N 张卡，各卡算一部分再通信合并权重单卡装不下；省显存为主，卡间需高带宽互联
数据并行 DP--dp N起 N 个完整模型副本，各自服务不同请求单卡装得下、追求吞吐；与 TP 可组合（如 --dp 2 --tp 2）
专家并行 EP--ep-size NMoE 模型的"专家"分散到 N 张卡，各卡只存一部分专家MoE 模型（如 DeepSeek、Qwen3.6-A3B 系列）超大专家表时
Prefill/Decode 分离--disaggregation-modePrefill 与 Decode 用不同机器/实例，中间传 KV Cache超大规模生产；两阶段资源画像完全不同时
官方口径TP 的首要目的是省显存而非提速；显存够用时，DP 对吞吐更友好。中小规模部署优先想清楚"权重 + KV 池"到底需要几张卡，再决定 TP/DP 组合。

3.7 量化：FP8 / AWQ / GPTQ

量化 = 用更少的比特存储权重（以及可选的 KV Cache），换来显存减半甚至更多、带宽压力更小、吞吐更高，代价是可能有轻微精度损失（必须用基准任务验证）。SGLang 分两类：

离线量化（推荐）
  • 权重已被人预先量化好（GPTQ、AWQ、FP8 官方版等），直接下载加载
  • 启动时无需任何 --quantization 参数，框架从 HF config 自动识别
  • 质量经过验证，优先选这条路线
在线动态量化
  • 加载 FP16/BF16 原版权重，启动时加 --quantization fp8 现场量化
  • 方便，但精度与性能通常不如专门校准的离线版本
  • 另有 --torchao-config int4wo-128 等选项

另一根杠杆是 KV Cache 量化：--kv-cache-dtype fp8_e5m2 让 KV 池容量近似翻倍。还可以叠加 --enable-torch-compile（编译小批量内核）与 CUDA Graph（消除内核启动开销，默认开启）进一步提速。

3.8 投机解码（Speculative Decoding）

Decode 串行慢的本质是"一步只验证一个 token"。投机解码用一个小而快的草稿模型连续猜 K 个 token，再让大模型一次前向并行验证——猜中的部分等于"一步生成 K 个 token"，接受率越高加速越明显（输出分布与原模型保持一致）。SGLang 内置 EAGLE 等算法支持（--speculative-algorithm EAGLE + 草稿模型），适合草稿模型可得且接受率高的场景；其代价是显存与工程复杂度，建议先跑通基线再试验。

5.6 结构化输出实战：让模型 100% 输出合法 JSON

这是 SGLang 的看家能力之一（原理见 3.5 节）。三种约束方式：JSON Schema（最常用）、正则、EBNF 文法，同一请求三选一。

JSON Schema + Pydantic（推荐姿势）

pythonjson_output.py
from pydantic import BaseModel, Field
import openai

class CapitalInfo(BaseModel):
    name: str = Field(..., pattern=r"^\w+$", description="首都名称")
    population: int = Field(..., description="人口数量")

client = openai.Client(base_url="http://127.0.0.1:30000/v1", api_key="None")
response = client.chat.completions.create(
    model="qwen/qwen2.5-0.5b-instruct",
    messages=[{"role": "user", "content": "请以 JSON 格式给出法国首都的信息。"}],
    temperature=0,
    max_tokens=128,

正则与 EBNF 约束

pythonregex_ebnf.py
# 正则：答案必须是固定枚举之一
response = client.chat.completions.create(
    model="qwen/qwen2.5-0.5b-instruct",
    messages=[{"role": "user", "content": "What is the capital of France?"}],
    max_tokens=16,
    extra_body={"regex": "(Paris|London|Berlin|Rome)"},
)

# EBNF 文法：更复杂的结构（GGML BNF 格式）
ebnf = """
root ::= city | description
city ::= "London" | "Paris" | "Berlin" | "Rome"
description ::= city " is the capital of " country
country ::= "England" | "France" | "Germany" | "Italy"
"""
response = client.chat.completions.create(
    model="qwen/qwen2.5-0.5b-instruct",
    messages=[{"role": "user", "content": "Give me the information of the capital of France."}],
    max_tokens=32,
    extra_body={"ebnf": ebnf},
)
注意① 约束只保证格式合法，提示词里仍应说明期望内容，质量才好；② 默认约束后端是 XGrammar（推荐保持默认），切换需在启动服务时加 --grammar-backend outlines 或 llguidance（Outlines 不支持 EBNF）；③ 离线 Engine 同样支持（sgl.Engine(..., grammar_backend="xgrammar")）。

6启动参数详解与性能调优

SGLang 的参数有上百个，但日常调优真正高频的只有十几个。本章给出速查表 + 调优决策树 + 压测方法，覆盖 90% 的实战需求。

难度：进阶动手 · 含压测命令

6.1 常用启动参数速查表

参数默认作用什么时候动它
--model-path—模型路径（本地目录或 HF 仓库 ID）必填
--tp N1张量并行卡数，权重切分到 N 张卡单卡装不下权重时；目的是省显存而非提速
--dp N1数据并行副本数显存充足追求吞吐；可与 TP 组合
--ep-size N1MoE 专家并行（配合 --enable-ep-moe）MoE 模型专家表过大时
--mem-fraction-static≈0.9预分配给权重+KV 池的显存比例OOM → 调小（如 0.7）；KV 池构建失败 → 调大
--chunked-prefill-size自动预填充分块大小长 prompt Prefill OOM → 调小（如 4096）
--max-running-requests自动最大并发请求数按业务 QPS 与显存设定
--context-length取自模型 config最大上下文长度不要擅自改大——可能引发异常行为
--max-total-tokens自动KV 池 token 容量上限主要用于调试，不是常规调优手段
--kv-cache-dtypeautoKV 缓存类型设 fp8_e5m2 让 KV 池容量近似翻倍
--quantizationauto权重量化方式在线量化时用（如 fp8）；已量化模型不要重复指定
--schedule-policyfcfs等待队列调度策略按负载特征调整
--enable-torch-compile关torch.compile 编译内核小模型/小批量场景提速；编译慢但可缓存
--stream-interval1流式吐字间隔步数越小越流畅，越大吞吐略高
--enable-metrics关导出 Prometheus 监控指标生产环境建议开启
--enable-hierarchical-cache关开启 HiCache 分层缓存多轮/长上下文/多实例共享前缀场景（配 --hicache-ratio、--hicache-write-policy 等）
--attention-backend自动注意力内核（fa3/flashinfer/triton…）FlashInfer 报错时退回 triton
--disable-radix-cache—关闭前缀缓存仅调试用，正常保持默认（开启）
踩坑--disable-cuda-graph、--disable-radix-cache 这类关闭项默认都别碰——它们只用于定位问题，保持关闭状态会白白损失性能。唯一例外：torchao 的 int8dq 与 CUDA Graph 有已知冲突，需 --disable-cuda-graph。

6.2 显存与调度调优决策树

bashdecision_tree.txt
启动失败/报错时按顺序排查：

CUDA out of memory（权重加载阶段）

  └─ --chunked-prefill-size 调小（如 4096）

  └─ 加 --enable-p2p-check
吞吐不达标
  └─ ① 确认 radix cache 开启、前缀命中率高
     ② 压测 --max-concurrency 逐级上调找拐点
     ③ 显存富余 → 考虑 --dp 副本 或 --kv-cache-dtype fp8_e5m2

7实战：部署 Qwen3.6-35B-A3B-FP8（含鲁班 GPU 环境适配）

本章把前六章的知识全部串起来：在鲁班（Luban ML）平台的 H20 GPU 环境中，部署你本地已下载的 Qwen/Qwen3.6-35B-A3B-FP8（MoE，总参 35B / 激活 3B，约 35GB，支持 262K 上下文）。

难度：进阶动手实战环境：鲁班平台 · H20 · ceph 存储

7.1 认识部署对象：MoE + FP8 意味着什么

🧩
MoE：35B 参数，3B 激活

总参数 35B 决定显存下限（权重都要装下），每 token 仅激活 3B 决定计算量小——Decode 快、吞吐高，是"显存贵、算力富余"的典型画像。

🗜️
FP8 官方量化

权重约 35GB（FP16 版要 70GB），细粒度 block=128 量化，质量与 BF16 几乎一致。SGLang 可直接加载，无需再加 --quantization 参数。

📏
262K 超长上下文

上下文上限 262144 token。KV Cache 随上下文线性膨胀——服务真实长文本时，KV 池容量与 --context-length 设置需要一起权衡。

🎛️
EP 专家并行可选

MoE 的专家可切分到多卡（--ep-size）。多卡部署时在"纯 TP"与"TP+EP"之间选择，大专家表时 EP 更省显存通信。

7.2 硬件规划：需要几张 H20？

鲁班平台 GPU 环境以 NVIDIA H20（96GB HBM3）为主。做一遍第 1.4 节的显存账：

估算h20_planning.txt
权重（FP8）                ≈ 35 GB
激活值/框架开销（预留）     ≈ 5 ~ 8 GB
可用于 KV Cache 池（--mem-fraction-static≈0.9 时）

单卡 H20 = 96 GB：
  tp=1：96 − 35 − 8 ≈ 53 GB KV 池 → 单卡就能装下权重，可跑中小并发
  tp=2：每卡权重 17.5GB，两卡共 ≈ 140GB KV 池 → 长上下文/高并发更从容
  tp=4：每卡权重 8.75GB，KV 池极大 → 262K 长上下文 & 高并发压测首选

结论：
  · 体验/功能验证        → 1×H20 即可起步（tp=1）
  · 常规服务（8~32K 上下文）→ 2×H20（tp=2）
  · 长上下文生产服务      → 4×H20（tp=4），并发余量最大
为什么推荐 tp=4 起步H20 是显存大、带宽相对受限的卡型：MoE + FP8 下 Decode 计算压力不大，瓶颈更偏显存容量与带宽——多切几份权重（TP）能让每卡的 KV 池和带宽压力都下降，对 262K 长上下文的"载重"场景收益直接。鲁班训练资源参考：30B~40B 模型对应 32 卡训练（微调场景），而推理部署只需其中一小部分卡。

# 变体 4：推理模型输出解析（如模型输出含思考过程，按 qwen3 规则拆分 reasoning）
python3 -m sglang.launch_server --model-path $MODEL_DIR --tp 4 --reasoning-parser qwen3 --port 30000
踩坑：不要画蛇添足FP8 版模型已量化，启动命令中不要再加 --quantization fp8——框架会从模型 config 自动识别，重复指定反而可能走错内核。同理，除非确认模型是"推理型"，--reasoning-parser 也不用默认加。

8常见问题排查（FAQ）

按"症状 → 处方"组织，覆盖安装、启动、运行三个阶段的高频问题。

难度：入门排错手册
启动阶段：CUDA out of memory

区分两种 OOM：加载权重阶段 OOM → 权重太大，加 --tp 卡数或换量化版模型；KV cache 分配阶段 OOM → 调小 --mem-fraction-static（如 0.7），给激活值和框架开销留空间。反之若报 KV 池构建失败/容量为 0，则调大该值。

长 prompt 推理时 OOM（权重明明装下了）

这是 Prefill 的瞬时激活值吃满显存。调小 --chunked-prefill-size（如 4096），把长输入拆块计算。

多卡报 "peer access / P2P not supported"

卡间 P2P 直连不可用（虚拟化/跨 NUMA 常见）。加 --enable-p2p-check 让框架显式检测并回退通信路径。

CUDA_HOME / 编译相关报错

设置 export CUDA_HOME=/usr/local/cuda-<版本>。使用 FlashInfer 出错（较老设备 sm75+）时，退回：--attention-backend triton --sampling-backend pytorch。

Docker 里跑一段时间就崩溃 / 多机死锁

① 共享内存不足：Docker 加 --shm-size 32g --ipc=host，K8s 更新 /dev/shm；② 多节点 TP 死锁：先尝试 --disable-cuda-graph 定位是否与 CUDA Graph 捕获相关。

模型从 HuggingFace 下载失败 / 很慢

国内环境先 export HF_ENDPOINT=https://hf-mirror.com；gated 模型设置 HF_TOKEN。生产环境最佳实践：在能联网的机器上把权重整仓下载到 ceph/共享盘（参考第 7 章），服务端只引用本地路径。

加载 FP8/AWQ 模型后要不要加 --quantization？

不要。预量化模型从 HF config 自动识别量化方式，重复指定可能选择错误内核。只有加载 FP16/BF16 原版并希望现场量化时才加 --quantization fp8。

吞吐远低于预期

按顺序检查：① 前缀缓存是否被误关；② 用 bench_serving 的 generated-shared-prefix 数据集验证缓存收益；③ 逐步上调 --max-concurrency 找吞吐拐点；④ 显存富余时上 --kv-cache-dtype fp8_e5m2 或加 --dp 副本；⑤ 流式场景适度调大 --stream-interval。

TTFT 突然变高 / 流式输出一顿一顿

典型原因：超长 prompt 的 Prefill 阻塞 Decode → 开/调 --chunked-prefill-size；或并发过载导致排队 → 看 bench 输出的排队与 TTFT p99，下调 --max-running-requests 保护在线体验。

bench_serving 全部请求失败 / 401、403

核对 --backend 与端点类型、--host/--port/--base-url、--model 是否与服务端一致；需要鉴权时 export OPENAI_API_KEY=sk-...；查看脚本打印的预热（warmup）错误信息。

改大 --context-length 后行为异常

官方明确警告：擅自超过模型 config 的上下文长度可能导致异常输出。若确需超长上下文，确认模型本身支持（如 RoPE 缩放配置）且 KV 池足够，否则降低 --context-length 并依赖分块/多轮处理。

量化模型质量下降明显

量化不是免费的：上线前必须在自己的业务评测集上对比量化前后表现；优先选择官方/经过验证的量化版本（如本实战用的官方 FP8）；避免对已量化模型再叠加在线量化。
