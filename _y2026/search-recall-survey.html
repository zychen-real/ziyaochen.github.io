0.1 · 百亿规模的核心挑战

算力与时延的双重约束

百亿级别意味着：单次 query 候选常驻内存约 600 GB - 1.2 TB（按 64 维 PQ8 压缩估算）。要求端到端（召回+粗排）在 30-60 ms 以内完成，留给粗排推理的时间通常 ≤10 ms。这决定了召回必须用「ANN 倒排 + 双塔」，粗排必须用「轻量交互 + 多任务蒸馏」。

冷启动与长尾

在通用搜索场景，新文档占比可达 10-25%/天。纯向量召回的 embedding 存在索引不全的问题，需要「倒排快速截断 + 向量兜底」。

多模态与异构

图文、视频、新闻、百科、问答，同一 query 可能意图多解。系统需要 多通道并行（按内容类型、按意图、按热度），而不是一塔打天下。

个性化与隐私

百亿语料下，多数 query 仍然是 短 query（1-3 词），单纯文本召回常常无解，需要引入用户行为序列、个人词表等个性化信号，但又要兼顾隐私合规与无状态首屏。

⚠️ 易踩坑
  1. 把召回当精排做：召回模型超过 100M 参数，单 QPS 立刻不可用。
  2. ANN 召回全量化：百万级 ANN 可用 OPQ/PQ，但百亿级必须用 IVF-HNSW 或 DiskANN，否则单节点内存放不下。
  3. 粗排与精排同质化：粗排 1ms 内必须打分，与精排同结构是不可能工程化的。
  4. 忽略尾部 query：热门 query 占 20% 流量贡献 80% QPS，但长尾 query 是 NDCG 损失大头。

1 · 召回层 Recall（10⁸ → 10³）

1.1 多路召回架构

百亿规模下没有任何单一召回通道能在 20ms 内覆盖 语义 / 字面 / 个性化 / 实体 / 跨模态 等所有信号。工业界普遍采用 多路召回 + 静态合并 + LTR 上下文融合 的范式：

📍 路（Lane）

每一路负责一种相似度度量：BM25、向量、个性化、实体、Tag。常见 6-12 路并行，每路返回 Top-K（K=200-500），总候选 ~10³。

🪜 优先级（Tier）

高优路（如倒排 + 热门词向量）直接进 Top-K；中优路做 ANN 多查询；长尾词向量放到 Auto-ReRank 层。

🔁 二阶段合并

通过 Contextual Ranker 模型（轻量 GBDT 或浅 DNN）把多路候选重排，得到 Top-10³ 给粗排。

路径一：倒排截断 + 双塔向量召回

经典工业范式。先用 BM25 / 倒排截断 砍掉 80% 不相关文档（O(1) 时间），再用 双塔向量 在剩余池中 ANN 检索，处理「近义改写、长 query、个性化语义」等问题。

路径二：多向量交互召回

对高优 query（占 5-10% 流量）走 ColBERT/PLAID，精度更高，单 QPS 用 5ms 换近 +5% Recall。

路径三：生成式召回

用 LLM 直接生成 docID/URL，适合「列表型 query」（如「最受欢迎的电影」），占召回 1-3% 流量但贡献 8-10% L1s 提升。

路径四：个性化 / 行为召回

用户近 30 天行为过 doc 的相似 item，作为一路独立通道。模型可以是 SASRec / TWIN / TWIN-v2。

关键设计原则

  • 多样优于精排：召回通道之间应保持 对偶性（duality），用新i.i.d. 通道补充现有漏斗，比优化单一通道 0.5% NDCG 更划算
  • 预算定额：每路候选 K 设上限（如 200），避免某一路爆量导致 top-K 偏移
  • 冷启动路由：新建频道走 canary + 5% 流量，确认 NDCG 后逐步放量
  • 失败兜底：BM25 必须 100% 可用，向量召回失败时降级到倒排

1.2 经典倒排召回

倒排（Inverted Index）是召回层的 0 号通道。它在小 query、高频词、精确匹配场景下仍优于任何向量方案。其核心思路：把 doc 切成 token，每个 token 维护一个 posting list（倒排表），query 求交后按 BM25 等打分。

评分公式演进

BM25 是工业标配，其评分：

score(q, d) = Σ∈q IDF(t) · ( f(t,d) · (k₁+1) ) / ( f(t,d) + k₁·(1-b+b·|d|/avgdl) )

其中 IDF(t) = log( (N-df+0.5)/(df+0.5) )，k₁≈1.2，b≈0.75。

深度倒排：DeepPA / DeepRank

BM25 假设词独立，对「同义改写」「上下文相关词」无能为力。DeepPA（Deep Passage Aggregation）系列把 BERT 引入 term-level 权重估计，再聚合到 doc-level：

score(q, d) = Σt∈q α(t, d) · SIM(φ(t), ψ(d))

其中 α 由 BERT cross-attention 学习，φ/ψ 分别是 term/doc 的轻量 embedding。

倒排召回工程要点（百亿级）

  • 分段索引（Sharding）：按 doc-id 哈希或 doc-source 分到 100-500 节点，单节点 2-10 GB posting list
  • Skip Pointer：高频词 posting 引入 skip 跳表，query 求交复杂度从 O(N) 降到 O(|q| · log N)
  • Top-K 截断优化：用 Max-Heap + 阈值早停（Threshold Algorithm），5-10ms 即可截到 K=1000
  • 编码压缩：doc-id 用 4 字节，term-id 用 3 字节，posting freq 用变长 (VByte/Frame-of-Reference)
  • 实时性：双 buffer（Double Buffer / FAggr / LSM 树）+ RT（Real-Time）索引，新文档分钟级可见
✅ 经验 倒排通道贡献基础 Recall 的 65-75%。在新系统的首版，先把倒排和 BM25 做到「行业前 20% 水平」，再考虑上向量召回；倒排质量不足时引入向量是事倍功半。

1.3 双塔向量召回（DSSM 系列）

双塔召回是百亿规模语义召回的事实标准。Query/Doc 各用一个 Encoder 产出 单一向量，以点积或余弦作为相似度。由于 doc embedding 可离线算好，召回阶段只需对 query 实时编码 + ANN 检索，单 QPS 极易扩展到 10k+。

1.3.2 训练范式

双塔训练的核心是 in-batch negative sampling + hard negative mining。

# 简化训练循环（PyTorch 伪代码）
q = query_encoder(q_input_ids)            # [B, d]
d = doc_encoder(d_input_ids)              # [B, d]

# In-batch：同 batch 其他样本视为负样本
scores = q @ d.T                          # [B, B]
labels = torch.arange(B)
loss_inbatch = F.cross_entropy(scores, labels)

# Hard Negative：来自 ANN 检索 Top-K 但非 gold
scores_hn = q @ hn_embedding.T             # [B, K]
loss_hn = F.cross_entropy(scores_hn.argmax(1), 0 ...) # 仅 Hinge / Margin

loss = loss_inbatch + λ·loss_hn

1.4 多向量交互召回（ColBERT / PLAID / MVR）

双塔的痛点是：query 和 doc 各自被压成一个向量，信息被压缩。对长 doc、跨句关联、低频专名场景损失巨大。多向量交互召回 在 2021 年后成为高优补充通道。

ColBERT (Khattab & Zaharia, 2020)

让每个 query token 和每个 doc token 都编码成向量，召回时计算 MaxSim 相似度：

score(q, d) = Σt∈q maxt'∈d <φ(t), ψ(t')>

Recall 显著优于双塔（+5-10% MRR@10 in BEIR），但 doc 侧向量存储大（每 doc 几十到上百个向量）。改进版 ColBERTv2 (2022) 把 doc 端压缩 + 用 PLAID 索引做近似 MaxSim。

PLAID (2022) 与后续

  • PLAID：把 colbert.doc_vectors 通过 centroids 聚类索引，检索时找候选 centroids，再做精确 MaxSim。百亿级单 QPS 50-100ms，已商用（Google、Meta）。
  • MVR (Multi-Vector Retriever, 2023)：通用框架，可插入任意交互式 encoder。
  • ColBERT-EMB (2024)：用 cross-encoder 把多向量压缩到一个向量，逼近 ColBERT 精度的同时保留双塔效率。

工程落地建议

  • 多向量仅作 高优 query 通道（占流量 5-10%），独立部署
  • Index 体积是双塔的 ~10x，必须用 PLAID / ColBERTv2 压缩
  • 在线 P99 控制在 30-40 ms，离线 GPU 批量重算 Top-K 再进粗排
  • 监控 增量 doc 的多向量构建 速率，建议分钟级异步重建

优势与挑战

优势

  • 不需要 ANN 索引，模型即索引
  • 可天然做「Top-K 列表解码」，一步出 recall 候选
  • 对接 LLM 易做「上下文学习」式零样本
  • 语义 docid 让相似 query 命中相近 docid

挑战

  • 训练难度大，docid 分配是关键
  • OOD query 退化严重，长尾覆盖差
  • 解码 Top-K 耗时（beam search / constrained），单 QPS ≤ 100
  • 工业系统普遍把它当作「高优补充通道」，不替代双塔
✅ 工业落地建议 生成式召回适合 列表型 / 高意图 query（"最好看的 10 部科幻电影"），作为一路独立通道，叠加在向量通道后。Google 在 2024 年公开的 ULTRON 已在 Search Generative Experience 中部分应用。

1.6 实体与链接召回

通用搜索中 实体词（人名/书名/电视剧/景点）占 query ~35%。仅靠文本匹配很难解决实体消歧（"苹果"是水果还是公司）、新实体冷启动（今年新出的电影）、实体联想（同主演的其他作品）等需求。

典型链路

  1. 实体识别（NER）：BERT-CRF / GLiNER (零样本) / LLM 抽取
  2. 实体链接（EL）：候选生成（知识库倒排）+ 链接消歧（BERT/复述）
  3. 实体扩展召回：KG 三元组（RDF / Neo4j）+ 同义/上下位扩展
  4. 融合进 doc 召回：把"匹配实体"作为一路召回，或把实体 embedding 与 doc embedding 拼接

2024-2025 新趋势

  • GLiNER (2024)：零样本多标签实体检测，无需训练即可识别新实体类型
  • LLM-EL：直接让 GPT-4 / Qwen2.5 做 mention-entity 链接，准确率高但延迟 200ms+，仅作离线候选生产
  • YAGO / Wikidata / CN-DBpedia 等开源 KG 持续更新；工业界普遍维护自有 KG，亿级节点
  • 实体 - 文档联合 embedding：把实体 / 文档 / query 投到同一向量空间，跨实体联想召回

实体召回在通用搜索的预期收益

  • 高实体 query 的 Recall@10 +3-5%
  • NDCG@10 提升 +1-2%
  • Zero-Result Rate 下降 -10-15%（针对新实体）
  • 用户 L1s「首位内容满足」+2-4%

1.7 个性化召回

通用搜索 query 越短越需要个性化。1-2 词的 query 在没有 user context 时常「无解」或「非用户想看」，需要根据用户的行为序列、地域、年龄、性别等做个性化。

用户表示

  • User-Tower 双塔：把用户历史序列（点击/收藏/搜索）经过 Transformer/SASRec/DIEN 编一个 user embedding，与 doc embedding 同空间，ANN 检索

1.8 多模态召回

2 · 粗排层 Pre-Ranking（10³ → 10²）

2.1 粗排在系统中的定位

粗排是召回后的第一道 模型化打分器。它承担三个角色：

  • 候选过滤：把召回层给出的 ~10³ 候选排序，选出 ~10² 交给精排
  • 上游知识载体：把召回结果按「粗排认为的最优」传递到精排
  • 流量再分配：通过粗排 NDCG 反推召回通道质量，为召回优化提供 A/B 反馈

粗排要在 ≤8 ms（单请求 P99） 内完成打分，意味着：

  • 模型参数 ≤ 50M（INT8 量化后 ≤ 200MB）
  • 在线特征 ≤ 50 个
  • 特征取值不可枚举（不能直接喂 1B 维稀疏 ID）
粗排 ≠ 精排 精排追求「点击 / 转化 / 互动」极致精度（300ms 内不计成本）。粗排追求 粗筛不失真 + 极致性能。如果你发现粗排 AUC 已经超过精排，那要小心：你可能是在一个被粗排污染过的样本分布上评估精排。

RankMixer 详解（Microsoft 2022）

RankMixer 抛弃 Transformer attention 结构，用「feature mixer + token mixer」两层大型 MLP 替代。优势：

  • 超参简单（layer 数、hidden size、activation）
  • 无 attention，ONNX/TensorRT 编译路径短
  • P50 推理速度比同等 AUC 的 DNN 快 1.5-2x
  • 已被多个搜索公司作为粗排 baseline

PEAR 详解（阿里 2023）

阿里妈妈公开的 PEAR 模型结构：

  1. 特征 embedding：所有 ID 特征分桶 embedding，连续特征离散化后 embedding
  2. Interaction Mask：显式 mask 控制哪些特征可以交叉（基于业务先验）
  3. Light Cross Layer：3-4 层 DCN-style cross layer
  4. MLP Tower：2 层 MLP 共享多任务塔
  5. 多任务损失：CTR + CVR + 互动率 + 时长

阿里公开的 PEAR AUC 数据（淘宝粗排口径）

  • DCN-v2 基线 AUC ≈ 0.7950
  • PEAR 模型 AUC ≈ 0.8035（+0.85pts）
  • 相同 AUC 下 PEAR 推理更快 35-40%
  • 线上 CTR +1.8%、GMV +1.2%（公开口径）

2.3.4 极简粗排（Light / Two-Tower）

2023 年起，一些工业系统开始试验 极简粗排：直接复用召回的双塔 + 在最后加一层浅层 cross。

  • 类似 Dual Encoder Augmented Ranking (DEAR) (Google 2021)
  • 类似 COIL (Columbia 2021)：检索式 ranking
  • 结构：score = α · cosine(q, d) + β · light_dnn(q_feat ⊕ d_feat)

优点：模型极小（<5M 参数）、单 QPS 5k+、与召回共享 embedding。缺点：AUC 比 DCN 低 0.5-1.5pts，需配合 GBDT 重排。

2.4 蒸馏与级联

粗排与精排的能力差距，可以通过 蒸馏 弥补，常见做法：

三种蒸馏范式

🔹 Logit 蒸馏

教师模型的 softmax 输出作为 soft label，学生模型训 KL 散度损失。简单、收敛快，但丢失序信息。

🔹 Rank 蒸馏（TAS-B 风格）

教师给出三连 (q,d⁺,d⁻) 相对序，学生用 margin loss 学。粗排主线方案。

🔹 List 蒸馏（ListNet/ListMLE）

教师对样本 list 给出 Top-K 概率分布，学生直接学 list-level 分布。计算量大但损失信息最少。

级联损失（Layer-wise）

# Cascaded Ranking Loss（简化版）
# 召回层教师 → 粗排学生 → 精排教师
loss_recall_to_prerank = KL(student_logits, teacher_logits)
loss_prerank_to_rank   = RankingLoss(student_ranking, teacher_ranking)
total = α·loss_prerank + β·loss_distill
✅ 蒸馏要点
  1. 教师模型必须比学生大 1-2 个数量级（如 GPT → MiniLM）
  2. 蒸馏损失 + 真实损失通常按 1:1 权重混合
  3. Incremental Distillation：每 2-3 个月重训教师，让学生稳定跟上
  4. 蒸馏可以跨召回/粗排/精排 whole-pipeline，效果更好但训练复杂

2024-2025 新趋势：LLM 蒸馏粗排

  • RankZephyr (2024)：用 GPT-4 给 query-doc pair 打分，蒸馏到 7B student
  • Qwen-Rank (2025)：阿里用 Qwen2.5-32B 做粗排教师，在线蒸馏到 0.5B
  • Generation-Augmented Rank (2024)：让 LLM 生成 doc 的「搜索预览」，粗排看到更丰富的特征

3.2 联合训练

召回和粗排本应联合优化，但因双塔架构和精排架构差异，传统实现往往解耦。2022-2024 起出现了一些 whole-pipeline 联合训练 方案：

  • Two-Stage Training：先训召回，再冻召回训粗排；最普遍但次优
  • Joint Embedding + Ranker：用 joint loss 同时训 query/doc embedding 和 final ranker
  • End-to-End Joint Training (EEJT) (2023, Microsoft)：用 re-parameterization 让召回与粗排同框架
  • Differentiable Retrieval (2024)：把 ANN 索引做成可微检索算子，端到端训练

Joint Loss 设计

L = α · L_recall + β · L_rerank + γ · L_kd
# α, β, γ 随训练阶段调整
# Stage 1: α=1, β=0       (pretrain recall)
# Stage 2: α=0.3, β=1     (joint train)
# Stage 3: α=0, β=1, γ=0.5 (distill)
⚠️ 联合训练的「梯度对齐」挑战
  1. 召回的 in-batch softmax 梯度与粗排的 pairwise loss 梯度方向不同
  2. 需要 梯度融合（GradNorm / GradVac）平衡各 loss
  3. 不能简单相加，否则某一 loss 会主导训练

诊断工具

  • 流量回放：把生产 query 列表发回离线系统，对比召回结果是否一致
  • 检索链路 tracing：给每个 query 打 trace_id，端到端追踪召回→粗排→精排
  • 漏斗分析：每一步的覆盖度、损失分布
  • A/B 实验：4-7 天观察窗口，统计显著性 95%

诊断常见问题清单

  1. 召回量足但粗排 AUC 下降 → 召回通道分布偏移，查新增 doc 是否进全量索引
  2. 粗排 AUC 正常但 L1s 跌 → 粗排候选中含过期 / 已删除 doc
  3. 延迟突增 → 大概率 ANN 索引崩溃或 GPU 资源被打满
  4. 新 query 召回为空 → 检查 NER、query 改写、字典更新

索引分层

  • L0：新文档 mini-index（最近 24h），Faiss flat + PQ8，几千万级
  • L1：近 90 天主索引，IVF-HNSW + PQ，亿级
  • L2：全量索引，ScaNN/SPANN，10¹⁰+，放 SSD
  • 查询顺序：L2 → L1 → L0，跨层合并取 Top-K

  • 查询分发到 100-500 节点（query → hash(qid) → node_id）
  • 每节点返回 Top-K_local，最终 merge 中心节点
  • 跨 shard 平衡：中心化协调器 或 两层结构（一层 coordinator，一层 shard）

4.2 GPU 粗排推理

百亿级粗排逐步从 CPU 转向 GPU，主要驱动力：

  • CPU AVX-512 推理 5ms/QPS 仍是大模型瓶颈
  • H100 TensorRT-LLM 单卡 25 万 QPS/s
  • GPU batching 节省空载功耗

GPU 推理栈

  • TensorRT-LLM (NVIDIA)：粗排 DNN 主力框架
  • vLLM / SGLang：粗排兼 LLM 重排
  • Triton Inference Server：多模型统一部署
  • ONNX Runtime GPU：粗排 CPU→GPU 过渡方案

典型部署

4.3 RPC 与服务化

召回粗排的 RPC 设计原则：

  • 多 RPC 协同：召回多路并行，每路独立 RPC，5ms timeout；任一路超时则降级
  • Stub 链路：召回 → 粗排 → 精排，pipeline，整体 P99 由多阶段相加
  • 本地缓存：高频 query 的召回结果缓存（命中率 20-40%）
  • 降级策略：满载时返回倒排前 100 + 热门粗排

5.1 Microsoft Bing

Bing 在 2023-2025 KDD / SIGIR 公开的多篇论文展示了完整的召回-粗排升级路径：

  • SETRank / UBR (2023)：用户行为驱动粗排，离线 AUC +1.4pt

Bing 公开口径

  • 全网索引量 ~ 30B 网页（2024）
  • 端到端 P99 200 ms，召回+粗排 P99 30 ms
  • 向量召回占比从 2020 的 30% 提升至 2024 的 75%
  • 粗排 GPU 推理占比 ~ 40%（夜间高峰）

5.2 Meta（Facebook / Instagram）

Meta 的搜索场景包括 Facebook Search（社交图搜索）和 Instagram Explore。公开报告：

Meta 经验 EBR 系统最大的工程难点是 doc 侧 embedding 不能实时更新（每天 batch 重训）。Meta 通过「近实时 user embedding + T+1 doc embedding」组合解决，长尾 doc 用人工审核 + 规则兜底。

6.1 按资源分梯度的优化方案

不同团队的资源和目标差异很大。下面按 团队规模 / 算力预算 / 时间窗口 给出三档推荐方案：

  • 融合：RRF（Reciprocal Rank Fusion）
  • 训练数据：用户行为 30 天曝光-点击对
  • 预期收益：基线 + 5-8% NDCG@10

🏎️ Tier 2：增长团队（5-30 人，100-2000 GPU·天/月）

  • 召回：BM25 + 双塔 + ColBERT 5% 高优 + 个性化 + 实体内嵌，5-8 路
  • 粗排：PEAR / RankMixer，多任务 ESMM/AITM
  • ANN：ScaNN / SPANN，GPU 索引 + 量化
  • 融合：LambdaMART (LightGBM) Contextual Ranker
  • 精排蒸馏：ListNet 蒸馏，双塔到粗排
  • GPU 粗排：TensorRT INT8
  • 预期收益：Tier 1 基础上再 + 3-5% NDCG@10

🛰️ Tier 3：顶级工业化（> 50 人，> 5000 GPU·天/月）

  • 召回：多路 + ColBERT + 生成式 DSI/ULTRON + 个性化，10+ 路

  • 可观测性：端到端 tracing + 自动化诊断
  • 预期收益：通用搜索长期 L1s 提升 8-15%

6.3 未来方向（2026-2030）

趋势 1：生成式检索（GR）的再起

2026 年，DSI / ULTRON / GenRet 在多篇 SIGIR / KDD 中显示了列表型 query 上的优势。下一步：

  • LLM-native retrieval：让 LLM 自身充当检索器，统一检索与生成
  • Multi-Granularity DocID：从 docid → URL → passage-id
  • Self-reranking：用 LLM 给生成候选重排，一致性强于独立 reranker

趋势 2：长上下文 + 多模态端到端

随着 LLM 上下文扩展到 1M+ tokens，「召回 → 粗排 → 精排 → 生成」的传统漏斗可能被「全上下文统一模型」替代。但短期（3-5 年）漏斗结构仍然是性能最优解。

趋势 3：Agentic Search（代理式搜索）

2026 年 LLM 工具调用能力大幅提升，「Search Agent」成为新形态：

  • query 改写 / 拆解 → 多轮检索 → 工具调用 → 答案生成
  • 每轮检索仍依赖召回 + 粗排 + 精排的成熟漏斗
  • PC7 (SANDBOX II) 正在做的工作

趋势 4：跨模态统一 embedding

BGE-M3 / NV-Embed / MM-Embed 等已在 text-image-audio-video 四模态上统一。LLM-based 多模态 embedding 将取代单模态 embedding 成为新的标配。

趋势 5：硬件协同（GPU + SSD + 内存）

  • GPU-ANN (NVIDIA cuVS, 2024)：H100 上 50万 QPS/s 10¹⁰ ANN
  • CXL 内存池：跨节点共享内存，10¹¹ 索引单节点可查
  • Persistent KV (SGLang)：粗排 KV 缓存复用，省 30% 延迟
✅ 总结：召回粗排优化的「不变」与「变化」

不变：

  • 漏斗结构（召回→粗排→精排）在 5 年内仍是 SOTA
  • 对偶性 + 多样性优先于单一通道极致优化
  • 性能-精度平衡永远是核心约束
  • 特征治理 + 可观测性是质量的地基

变化：

  • 通道数：3 路 → 10+ 路
  • 模型规模：LR → DNN → PEAR → LLM 蒸馏
  • 索引：全部 RAM → SPANN/SSD → CXL/GPU-ANN
  • 多模态：从单文本 → 图文音视频统一
  • 生成式：从辅助 → 主通道之一
